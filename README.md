# 小红书/抖音笔记评论监控，回写飞书多维表格

> 仓库叫 `linkcheck` 是沿用了已有的空仓库，和内容没关系。
> Python 包名 `xhsearch/` 是历史遗留，改它只有 churn 没有收益，就留着了。

把「每条帖子都要手动点开看评论区」变成「表格里自己就是最新的」。

每行一篇已发布的笔记，机器定期去取：**评论数**、**置顶评论内容**、**综合排序前 8 条评论**，
判断帖子是否失效/被限流，并把结论写进 `流量状态` 多选字段——**不覆盖运营手工打的标签**。

同一份第一页评论还会被查两遍，方向相反：`评论关键词` 查**我们自己种的评论显示出来没有**，
`负面词` 查**别人有没有在底下说难听的、或者提竞品**。两件事共用一次调用，不额外花钱。

> ⚠️ 负面这一列是**预警，不是普查**：它只看第一页（和 `评论区快照` 同一份），
> 埋在第二页往后的负面评论看不见。这是刻意的取舍——翻页按页计费，
> 一条帖子翻十页就是十倍成本。要做完整口碑普查，那是另一件事、另一笔预算。

## 一、先说三条做不到 / 会花钱的事

这三条决定要不要做、怎么做，放在最前面。

### 1. 抖音没有「置顶评论」这个能力

SocialDataX 的抖音评论接口返回：`comment_id / content / create_time / like_count /
reply_count / ip_location / image_urls / sticker / is_hot / is_folded / author`——
**没有 `is_pinned`**，只有"是否热评"和"是否折叠"；而且**没有 `sort_type` 参数**，排序不可控。

TikHub 那边是上游原始透传，条目里多了 `label_type` / `label_text`，
**看着像置顶标记但语义没验过**。代码里一律不判抖音置顶——
错判置顶比不判置顶伤害大得多。要验的话见 [`docs/待验证清单.md`](docs/待验证清单.md) 第 18 项，
成本 ¥0.007。

所以：

| 需求 | 小红书 | 抖音 |
|---|---|---|
| 评论数 | ✅ | ✅（需多调一次 detail 兜底） |
| 置顶评论内容 | ✅ | ❌ 接口无此字段 |
| 置顶成功判定 | ✅ | ❌ 接口无此字段 |
| 前 N 条评论 | ✅ 综合排序 | ⚠️ 平台默认序，口径与小红书不等价 |

代码里抖音行的 `置顶评论` 会如实写「—（抖音不支持置顶监控）」，**不留空**——
留空会被运营读成"没置顶"，而真相是"这个接口根本看不到"。
`评论状态` 那一列抖音行**完全不碰**，写任何值都是撒谎。

（`评论状态` 和 `负面状态` 匹配的是**评论正文**，不依赖置顶字段，所以这两列抖音同样有效。
不能判的只有置顶。）

### 2. 成本主要由刷新频率决定，其次才是走哪家

**双通道**：默认优先 TikHub，SocialDataX 兜底。单价差得很多：

| | 小红书 | 抖音 |
|---|---:|---:|
| TikHub（主） | ¥0.072/次 | **¥0.0072/次** |
| SocialDataX（备） | ¥0.10/次 | ¥0.10/次 |

抖音便宜 93%，小红书便宜 28%，整体省一半。完整对比和踩到的坑见
[`docs/供应商对比.md`](docs/供应商对比.md)。

接口都没有 `page_size` 参数，页大小服务端定（10–20 条），**取 3 条和取 20 条一个价**。

调用次数（实测核实）：

- **小红书 = 1 次**。评论接口一次同时返回 `comment_count`（笔记总评论数）、
  `is_pinned`（置顶就在第一页）、和综合排序的前一页评论。R1/R2/R3 一次拿全，**不需要额外调 detail**。
  只有想要点赞/收藏（热度判定的另一个维度）时才补一次。
- **抖音 = 2 次**。SocialDataX 的 `comment_count` 类型是 `integer|null`（"当前不可用时为 null"），
  为了"评论数"这列不间歇性变空，detail 必须恒定兜底。
  （TikHub 的 `total` 实测是实数，但 detail 还要拿点赞收藏，照调。抖音一次才 ¥0.007，无所谓。）

按每天新发 20 条、留存 30 天、小红书七成算（`python3 tools/estimate_cost.py` 可自己改参数重算）：

| 策略 | 调用/天 | 月成本（TikHub） | 月成本（SocialDataX） | 最坏陈旧度 |
|---|---:|---:|---:|---|
| **分层刷新（本项目默认）** | 639 | **¥946** | ¥1,918 | 新帖 8 小时 |
| 分层 + 关掉小红书 detail | 485 | ¥796 | ¥1,456 | 同上，但没有点赞/收藏 |
| 全表每天刷一遍 | 1,200 | ¥1,892 | ¥3,600 | 24 小时 |
| 纯手动点（按 15% 行被点到） | 126 | ¥186 | ¥378 | **无穷大** ⚠️ |

### 3. 「点一次刷一条」还是「刷全部」—— 两个都要，但主力不是按钮

这是你问的核心问题。答案是**分层自动刷新当主力，手动按钮当逃生口**，理由是钱和风险两头都站得住：

**成本上，"全表日刷"贵在没意义的地方。** 8–30 天那 460 条占在管总量的 77%，
在全表日刷里也吃掉 77% 的预算，而它们的数据几乎不动了。把这笔钱挪到新帖上，
花更少的钱换来更高的时效——这不是取舍，是同价位下的严格改进。

**纯手动的问题不在钱，在于最坏陈旧度是无穷大。** 没被点到的行永远不更新，
而**风控和封控恰恰是必须被动发现的事件**——靠运营记得去点，等于没有监控。

所以按钮的正确定位是三个具体场景：客户临时来问、疑似风控要复核、刚做完置顶要立刻验证。
代码里给按钮加了 **90 秒同行冷却**：有人连点 200 次 = 1 次真实调用。

## 二、架构

```
                    ┌──────────────────────────────────┐
   运营勾选          │      飞书多维表格（唯一的界面）      │
   「排队刷新」  ───▶ │  一行 = 一篇笔记                   │
                    │  流量状态 / 评论数 / 置顶评论 / 快照  │
                    └───────────┬──────────────────────┘
                                │ 读表 + 写回（开放平台 API）
                                ▼
                    ┌──────────────────────────────────┐
                    │  本项目（Railway 上的小服务）          │
                    │  链接识别 → 调接口 → 判定 → 合并标签   │
                    └───────────┬──────────────────────┘
                                │ 双通道，主挂了自动降级
                    ┌───────────┴───────────┐
                    ▼                       ▼
        ┌────────────────────┐  ┌────────────────────────┐
        │ TikHub（主）        │  │ SocialDataX（备）        │
        │ GET + query        │  │ POST + JSON            │
        │ api.tikhub.dev     │  │ mcp.socialdatax.com    │
        └────────────────────┘  └────────────────────────┘
```

两家的响应形状完全不同（一家是上游原始透传，一家是归一化过的），
差异全部挡在 [`xhsearch/providers.py`](xhsearch/providers.py) 一层里，
判定逻辑只认一种形状。

### 中间层是必需的，不是选择

飞书自动化的「发送 HTTP 请求」节点**没法自己完成这件事**，原因是它取不出数组里的元素。

要填「置顶评论」这一列，必须求值 `items[?is_pinned].content`。而飞书 HTTP 节点
只能整体引用数组，无法引用数组里的单个变量；循环节点也堵死了——循环体内不支持条件判断
（没法筛 `is_pinned`），循环结束后的节点又引用不到循环内的数据（没法攒前 N 条）。
**在飞书内部把数组拍平在结构上就做不到**，必须有个东西把数组变成标量。

这就是这个中间层存在的全部理由。它不需要 LLM，不需要状态，就是取数 → 拍平 → 判定 → 写回。

（顺带一提：走 MCP 端点的话还有第二个障碍——那条路的成功响应是 SSE 分帧，
而飞书 HTTP 节点靠"粘一段 JSON 样例"解析响应，喂 SSE 进去解不出来。
本项目改用 REST 端点后没这个问题，但拍平数组的问题依然在。）

### SocialDataX 那条通道用的是 REST，不是 MCP

同一个后端、同样的字段，但 REST 明显更好：

- **纯 JSON**，不用处理 SSE 分帧，也不用小心翼翼地拼 `Accept` 头
- **有一份公开可读、不需要 Key 的 OpenAPI 3.1 规范**，带完整错误码契约：
  `https://api.52choujiang.cn/socialdatax/api/v1/docs/openapi.json`

⚠️ 这个接口有一处很容易写错的地方：**业务错误也返回 HTTP 200**，
靠 body 里有没有 `code` 字段区分（规范原文：「请求成功；业务错误也会返回 200 + {code, message}。」）。
只看 HTTP 状态码的客户端，会把每一个「笔记已删除」当成成功。

错误码是权威的，不需要猜中文话术：

| code | 含义 | 处置 |
|---:|---|---|
| 1003 | 不存在或不可见 | 两击定罪 → 已失效 |
| 1006 | 权限/状态/平台限制导致不可读 ← **封控** | 两击定罪 → 已失效 |
| 1007 | 页面暂时不可访问 | 退避重试，**不判失效** |
| 1008 | 已删除（规范明写"不要重试"） | **第一次就定罪** |
| 1004 | 积分不足 | 整批停 |
| 1401 / 1429 | Key 无效 / 限流 | 整批停 / 按 `retry_after_seconds` 退避 |

`1007`（页面暂时打不开）和 `1006`（内容被限制）分开处置这一点很关键——
混为一谈就会把瞬时故障标成风控。

**TikHub 那条通道没有这张表**——它没有公开的业务错误码契约，失效判定只能靠
响应形状的启发式（空壳判活、detail 的 `data: []`、抖音的 `filter_list`）。
这是它唯一明显不如 SocialDataX 的地方，也是后者值得留着当备胎的理由。
详见 [`docs/供应商对比.md`](docs/供应商对比.md) 第三节。

### 触发通道

| 通道 | 怎么触发 | 飞书自动化配额 | 用途 |
|---|---|---|---|
| **A · 勾选 + 轮询** | 运营勾 `排队刷新`，后台每分钟扫表 | **0 次** | 手动入口，可拖拽批量勾 |
| **B · 分层巡检** | 后台定时任务 | **0 次** | 基线覆盖，风控/封控靠它发现 |
| ~~C · 按钮字段~~ | ~~点按钮 → 自动化 → HTTP~~ | ~~每次点击 1 次~~ | **不建议用，见下** |

**这个方案不用按钮字段，也因此不需要升级飞书套餐。**

飞书自动化运行次数是**按月、按租户共享**的配额，自动化和工作流共用。
当前套餐 200 次/月 ÷ 30 天 ≈ **每天 6.7 次**——几百条帖子的规模，
按钮点两下就没了。而且失败模式是**静默停摆**：表不报错，只是不更新，
更糟的是它会把**全公司**的自动化额度（合同、报销、排期）一起打光。

通道 A 是它的完整替代：**一次配额都不消耗**，体验差别只有"最多等一分钟"，
而且能拖拽批量勾 50 行，按钮反而只能一行一行点。处理完机器自动把勾去掉——
**勾消失就是"已完成"**，不需要向运营解释任何东西。

升级套餐的钱花在数据接口上更值。

## 二·五、监控面板：表多了以后怎么看

飞书表是**行级**的工作台，一张表一个项目。表多了以后有个具体的麻烦：
真正要人管的行（`风控中` / `有负面` / `置顶掉了` / `已失效` / `刷新失败`）
在每张表里都只有零星几行，埋在几百行里——**没有跨表视图，就只能一张张点**。

```bash
python3 cli.py serve      # 常驻、只读、一个付费请求都不发
```

面板是 Railway 上的**第二个服务**，最上面是一张跨表待办列表：所有项目里
要处理的行拉平成一张表，每行带 `诊断信息` 原文和一个「去这一行」的直达链接。

> **分工：面板负责发现，飞书负责处理。**
> 「这个项目现在什么情况、哪儿出问题了」在面板上看完；回飞书只发生在
> 面板已经把你带到具体某一行的时候。

它**不会**成为第二个付费执行者：不 import 供应商那一层、不调任何会发付费
请求的函数，有测试按 AST 逐个调用节点钉死这一条。要刷新就去表里勾
「排队刷新」，cron 五分钟内接手——和运营手工勾是同一条路。

完整说明（每个数字什么意思、怎么部署、安全上做了什么没做什么）见
[`docs/面板.md`](docs/面板.md)。

## 三、跑在哪

**主方案是 Railway**，手把手步骤见 [`docs/Railway上线手册.md`](docs/Railway上线手册.md)；
其他选项（GitHub Actions / 自建 VPS）见 [`docs/部署.md`](docs/部署.md)。

选 Railway 的理由只有一条，但它比其他所有差异加起来都重要：
**它直接连 git 仓库部署。** `git push` 就自动重新上线，跑的永远是仓库里那一版。
这套东西每天往表里写几百次、运营完全依赖它，「跑的是哪一版」必须是确定的。

| | Railway | GitHub Actions | 自建 VPS |
|---|---|---|---|
| 勾选后多久有反应 | 5–10 分钟 | 10–70 分钟 | 1 分钟 |
| 代码从哪来 | ✅ git 仓库 | ✅ git 仓库 | ✅ git 仓库 |
| 单次执行上限 | 无 | 6 小时 | 无 |
| 服务器位置 | 境外 | 境外 | 可选 |

> **扣子路径已归档**：早期版本维护过「打包成单文件粘进扣子代码节点」的并行
> 运行时。定下 Railway 之后它已从主干移除——那条路跑的是一份粘贴的副本，

## 四、防止写坏表的五处设计

这是整个项目里最该被理解的部分。运营对表的信任一旦丢了就补不回来。

### 1. 标签合并：人工标签永远不动

飞书多选字段的写入是**整体覆盖**，没有原子 append。所以必须读-改-写：

```
新值 = (现有标签 − 机器命名空间) ∪ (本次算出的标签)
```

而「读」发生在整轮开跑时、「写」发生在整轮收尾时，中间隔着几分钟的付费调用。
所以**写回之前会再读一次这一列**，用那一刻的现值重做一次合并（乐观并发控制）：
运营在这几分钟里手工加的标签不会被开跑那一刻的旧快照覆盖。
重读失败时（网络、权限）这一列干脆不写——宁可这一轮少打一个机器标签
（下一轮自动补上），也不能覆盖人手打的标签。

机器只认 `观察中 / 无水花 / 评估中 / 爆贴 / 大爆 / 风控中 / 疑似限流` 这七个词，
其余一切（`已复盘`、`客户确认`，以及运营未来新增的任何选项）**机器零权限**。
（旧版打过的 `已失效` 已并入 `风控中`，残留旧值会被自动摘掉。）

热度档位（发布不满 48h 且 <20 观察中，48h 后仍 <20 无水花，≥20 评估中，
≥50 爆贴，≥100 大爆）**互斥且只升不降**：每轮只留最高的一个；评论被删导致
数字掉下去不该让帖子从「大爆」退回「爆贴」，那种异常由 `疑似限流` 表达。

`观察中` 这一档是 2026-08 补的，治的是「新发的一批帖子 `流量状态` 全是空的、
只能手工去填」。以前冷启动窗口内的行**一个标签都不打**，而空格在运营眼里
分不出「还没轮到它 / 轮到了没结论 / 机器坏了」。它到 48h 会自动升成
`无水花` 或更高档，不需要任何人去清。**要先在飞书把这个选项建好**
（`doctor` 会点名），不想要就设 `TAG_OBSERVING=` 关掉。
另外，`发布时间` **空着或填成未来**的行算不出发布多久、热度判不了。这两种情况
都不打 `观察中`（未来时间同样满足「不足 48 小时」，打上去等于用一个看着合理的
标签把日期错误盖住），而是在 `诊断信息` 里说清是哪一格有问题，改好下一轮自动补判。
表里已经有档位时这句话照样会报——最难发现的正是一行卡在 `观察中`、
发布时间却是坏的，于是它永远熬不到 48 小时、永远升不成 `无水花`。

`风控中` **只认硬证据**：上游返回了审核/受限标记，或链接失效（两击定罪）。
评论数的异常都不进风控——腰斩是 `疑似限流`，起不来是 `无水花`，
口径分开，运营才知道每个标签背后是什么证据。
`风控中 / 疑似限流` 是易变的，每轮重算，恢复正常自动摘掉，否则表会越来越红。

**无变化就根本不写这个字段**——省一次写，也不让人看到这行被反复改动。

### 2. 两击定罪：一次失败不判死

一次网络抖动或上游话术改版，就把好帖子标成"风控"，运营会全线停投。

所以第一次取不到内容只写「疑似受限」并计数，**一个标签都不打**；连续两次才定罪
（巡查状态写「已失效」，流量状态打 `风控中`）。任何一次成功都会把计数器清零。

### 3. 全局熔断：批量失效 = 上游故障，不是内容出事

一批里判定失效的比例超过 20%（且样本 ≥ 10 行）→ **整批撤销标签写入**。

几百条笔记不可能在同一小时里被集体删除。真出现这种情况，一定是上游挂了或者错误话术改版了。
宁可这一轮什么都不写。

比例这道闸要 10 行样本才生效，而 `queue` 一批常常只有三五行，所以还有第二道：
一批里**每一行**都判了失效、而且**都栽在同一个非权威错误码上**（≥3 行）
也会熔断。「非权威」是关键——真被删掉的内容拿到的是有契约的权威码
（SocialDataX `1008`、TikHub 小红书 detail 返回空列表），它们不受这道闸影响，
所以一张只有三行、三条都真被删了的表照常能判「已失效」。

熔断作废得**彻底**：被保护的行不但不改流量状态，也**不推进「最近检查时间」、
不清「排队刷新」的勾**——否则调度器会以为这一行本轮处理完了，运营的手动请求
被吞掉，下一次复查还要再等 8–72 小时。

另外：**任何失败路径都不清空数据列**。`评论数`、`置顶评论`、`评论区快照` 保留上一次的成功值——
清成 0 会制造"爆贴突然归零"的假警报。

### 4. 单轮硬预算 + 运行租约：花钱这件事必须有上界

两个独立的闸门，防的是两种不同的失控：

* **硬预算**（`MAX_RECORDS_PER_RUN` / `MAX_CALLS_PER_RUN` / `MAX_YUAN_PER_RUN`）
  在**发请求之前**预留额度。任一闸门触顶就停止派发新行，已到手的结果照常写回，
  没轮到的行保持原样（排队勾还在、检查时间没动），下一轮自然继续。
  没有它的时候，「全表被勾上排队刷新」或「最近检查时间列被误清空」这类事故的
  单轮成本是没有上界的。
* **运行租约**（`xhsearch/runlock.py`）保证同一时刻只有一个付费执行者。
  拿不到租约的进程干净退出，一个请求都不发。
  ⚠️ 它是**文件锁**，只在同一台机器/同一个文件系统上生效——跨主机
  （Railway 两个服务、Railway + Actions）挡不住，那要靠部署纪律：
  **定时调度只能有一个地方跑**，见 [`docs/部署.md`](docs/部署.md)。

### 5. 日志和表必须能对上

写坏表会丢信任，**说不清自己干了什么**同样会。出过一次
「日志和表里的记录对不上，尤其是巡查时间」，三个原因叠在一起：

* 容器日志行首的时间戳是 **UTC**，表里那一格是飞书按租户时区渲染的**北京时间**——差 8 小时
* `最近检查时间` 盖的是**整轮开跑**那一刻，几百行共用一个值，比日志里那一行早好几分钟
* stdout 不接终端时 Python 默认**块缓冲**，几十行攒够 8KB 才一起吐出去，
  云平台按收到的时刻给整块打同一个时间戳、块内顺序还会乱——
  线上真出现过表头跑到结论后面、「已写回 8 行」打完了还在出逐行结果

现在：**每一行盖自己处理完的那一刻**，行首直接打印那个值（按
`DISPLAY_UTC_OFFSET` 渲染，默认 +8），和表里那一格逐字相同；
stdout 改成逐行 flush，每一行都带自己真实的时刻和真实的先后顺序：

```
⏱ sweep 开跑：2026-08-26 08:07:14 +08（UTC 00:07:14，容器日志用的就是这个）
  [08:07:21] recvs93vQ1qhHs → 正常 发布 32 小时评论数 4，还在 48 小时冷启动窗口内，暂不下结论 → 观察中
已写回 12 行，本轮「最近检查时间」= 2026-08-26 08:07:21 +08 ~ 08:07:46
```

`[  --  ]` = 这一行本轮**没有**推进时间戳（冷却跳过、留待下一轮、熔断作废）。
还有一种「对不上」不是 bug：sweep 和 queue 通常是两个独立的定时任务、各有各的日志，
在一份日志里翻不到某一行，它多半是被另一个任务刷的——开跑那行会打出模式。

## 五、快速开始

```bash
# 1. 配置（复制后填写）
cp .env.example .env && vim .env

# 2. 体检：不花一分钱，检查权限/字段/选项是否齐全
set -a && source .env && set +a
python3 cli.py doctor

# 3. 只估算这一轮要花多少钱，不发请求
python3 cli.py estimate

# 4. 真跑
python3 cli.py sweep          # 分层巡检：只刷到期的行
python3 cli.py queue          # 只刷勾了「排队刷新」的行
python3 cli.py row recXXXX    # 刷指定行（无视冷却和分层节流）

# 测试（全离线，不需要 API Key）
python3 -m unittest discover -s tests -t .
```

数据供应商的选型见 [`docs/供应商对比.md`](docs/供应商对比.md)。

## 七、代码结构

```
xhsearch/
  links.py       链接识别：判平台、抽 ID。纯函数，不发请求
  protocol.py    SocialDataX 协议：组包、解包、官方错误码归类。纯函数
  providers.py   双通道：两家的组包/归一化/错误分类都挡在这一层。纯函数
  analyze.py     评论页 → 指标/置顶状态/快照文本/标签判定。纯函数
  tags.py        多选字段合并算法。纯函数
  rows.py        行模型 + 调用计划（这里决定花多少钱）。纯函数
  config.py      列名映射与判定口径 ← 唯一需要按你们表结构改的文件
  envfile.py     .env 加载（严格小解析器）
  transport.py   HTTP（标准库，零依赖）：重试、退避、响应体上限
  runlock.py     运行租约：同一时刻只允许一个付费执行者
  feishu.py      多维表格读写
  runner.py      编排：读表 → 调接口 → 判定 → 写回
  schema.py      表结构的期望值和体检判据。纯函数（doctor 和面板共用同一份）
  summary.py     跨表聚合：一批 record → 一个项目的快照。纯函数
  panel.py       监控面板的 HTTP 服务。**只读，一个付费请求都不发**
  panel_view.py  面板的单文件 HTML（内联样式和脚本，零外部资源）
cli.py           命令行入口
tools/
  estimate_cost.py     按配置算月度成本（两家分开报）
  probe_channel.py     拿一条真实链接把某条通道走一遍（会真扣费）
tests/           560+ 个测试，全离线
```

分层的用意：**纯函数和网络严格分开**。核心逻辑能在本地毫秒级跑完
全部测试，不需要任何 Key；换运行时也只需要换传输层。
