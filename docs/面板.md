# 监控面板

一屏看完所有项目的健康度和待办，不用一张张点开飞书表。

```
python3 cli.py serve
```

它是 Railway 上的**第二个服务**，常驻、只读。**一个付费请求都不发。**

---

## 一、它解决的是什么

表少的时候飞书表本身就够用。表多了以后有一个具体的麻烦：
真正要人管的行（`风控中`、`有负面`、`置顶掉了`、`已失效`、`刷新失败`）
在每张表里都只有零星几行，埋在几百行里——**没有跨表视图，就只能一张张点**。

所以这个面板的主角不是统计图，是最上面那块**跨表待办**：
所有项目里要处理的行都在这儿，**每个项目一个标签页**，标签上带条数
（红 = 这个项目里有风控 / 失效 / 刷新失败），页内按严重度排序；
每行带一个「去这一行」的直达链接，点进去就是飞书里的那一行。
标签顺序跟下面「各项目」一致（注册表顺序），不按严重度重排——位置每次
刷新都跳的话找不到自己的项目，严重度靠数字的颜色说。只给有待办的项目开标签。
上次看的是哪个项目记在你自己的浏览器里，重载后回到同一页。

> **分工：面板负责发现，飞书负责处理。**
> 「这个项目现在什么情况、哪儿出问题了」在面板上看完；
> 回飞书只发生在一种时候——面板已经把你带到具体某一行，你去处理那一行。

## 二、页面上每个数字什么意思

### 顶栏

| | 含义 |
|---|---|
| 在管行数 | `是否巡查` 勾着的行。取消勾选就是「这行别管了」，一个数字都不进 |
| 要人管 | 下面待办列表的行数 |
| 到期待刷 | 按分层策略该刷了的行。和 `cli estimate` 是**同一个函数**算的，数字逐字相同 |
| 预计花费 | 上面那批行刷一遍的钱。按每个平台实际会走的那家计价 |
| 排队中 | `排队刷新` 勾着、等 cron 接手的行。待办表里这样的行在「最近检查」旁标着「排队中」——标记在就说明看到的还是旧结论 |
| 卡住了 | 见下 |

### 「到期」和「卡住了」不是一回事

- **到期** = 下一轮该刷它。cron 每 5 分钟跑一轮，所以**任何时刻都有一批刚到期的行**，
  这个数字大不代表出问题。
- **卡住了** = 超过它应有间隔的**两倍**还没被刷到，或者在管、没归档、却从来没刷过。
  这个数字不为零才是要查的：多半是预算触顶、一直报错、或者调度根本没在跑。

归档的行（超过 `archive_after_days`）本来就不再自动刷，永远不算「卡住了」。
发布时间读不出来的行也不算——那是那一格有问题，`诊断信息` 里已经在报了。

### 关键词覆盖度

```
评论关键词  已填 34/120（86 行没填）
负面词      已填 86/120（34 行没填）
```

这一行治的是一个具体的困惑：`评论状态` 和 `负面状态` 那两格空着的时候，
运营分不清是「机器没判」还是「这行压根没填词」。

按设计，**没填词的行机器完全不碰那两列**。把「86 行没填」摆出来，那些空格就有解释了。

> 关键词**不在面板上填**。它逐行可能不一样、又是多选列，在飞书里点选更顺手。
> 面板只负责告诉你哪几行还空着，点进去填。

### 待办为什么会出现在列表里

| 原因 | 什么意思 |
|---|---|
| `风控中` | 上游给了审核/受限标记，或链接两次取不到内容。**人工去平台确认** |
| `已失效` | 同上，连续两次取不到 |
| `刷新失败` | 网络/接口故障，**表里已有数据一个都没动**。看诊断信息 |
| `有负面` | 第一页评论里命中了负面词或竞品词 |
| `疑似限流` | 评论数相对上次腰斩 |
| `疑似受限` | 第一次取不到内容，还没定罪，下一轮会复核 |
| `置顶掉了` | 以前置顶成功过，现在没了 |
| `卡住了` | 见上 |

排序就是处理顺序：风控/失效 → 刷新失败 → 有负面 → 疑似限流 → 卡住了 → 置顶掉了。

面板**不自己重新判一遍**热度或掉量，只报机器已经下过结论的事。
不然就会出现「面板说是爆贴、表里写着评估中」——两个都不能信。

#### 「哪一条」那一栏

待办表第二栏是这一行的短标识，给的是**笔记内容前十来个字**——
拿它去飞书表里 Ctrl+F 就能定位，不用一条条点「去这一行」开新网页
（那个链接是兜底，不该是主路径）。鼠标停上去显示完整文本；
顶栏那个筛选框也吃这一栏，可以直接打几个字筛。

列名不用配，面板自己在表里找，按这个顺序取第一个存在的列：

    笔记内容 → 文案 → 笔记标题 → 标题 → 内容

一个都没命中的话，退回用「反馈链接」那一格**抠掉链接之后**剩的文字
（小红书分享文案开头往往就是笔记标题），再退回笔记 ID。
**不会拿整格原文的前几个字顶上**——那样每一行都是
`https://www.xiaohongsh…`，一模一样，等于这一栏没显示。

找不到内容列时，项目卡上会写出来试过哪几个名字。要么在飞书里把那一列
改名成其中之一，要么设 `PANEL_LABEL_COLUMN` 指过去（配了就**只认它**，
表里没有那一列会被点名，而不是悄悄换一列——悄悄换等于配置没生效却没人知道）。

### 运行历史

页面下半部分是从 Railway 日志里还原出来的运行记录：每一轮什么时候开跑、
哪些表、处理了多少行、花了多少、有没有熔断/降级。

要它工作需要两边都设：

1. **cron 那个服务**加 `RUN_LOG_JSON=1` —— 日志里才有结构化事件
2. **面板服务**加 `RAILWAY_API_TOKEN` + `RAILWAY_ENVIRONMENT_ID`
   （建议再加 `RAILWAY_CRON_SERVICE_ID`，否则面板自己的访问日志会把巡检输出
   挤出翻页窗口）

用的是 `environmentLogs` 而不是 `deploymentLogs`：Railway 官方文档没写清
cron service 每次触发是新建 deployment 还是复用同一个，而环境级的查询对
两种情况都成立。

> **「没跑完」这一行要当回事。** 有 `run_start` 没 `run_end` 的轮子，
> 是被容器杀掉的形态（redeploy、回收、OOM）——那几轮已经付过钱的结果多半丢了。
> 面板会把这种轮子单独标出来并计数。

> ⚠️ **日志保留期是硬上限**：Hobby 7 天 / Pro 30 天。面板**不另存一份**，
> 所以运行历史最多往回看那么久。要看月度趋势得另想办法（比如让 cron
> 把每轮摘要写进一张飞书表），那是另一件事。

**日志里的密钥怎么处理**：送到浏览器之前，每一行都会对全部已知密钥
（TikHub / SocialDataX Key、飞书 App Secret、Railway token、面板口令）
各脱敏一次，**先脱敏再截断**——反过来的话 Key 横跨截断边界时会漏半截出去。

### 批量勾「排队刷新」

待办列表每行前面有个复选框，选中之后点「勾『排队刷新』」。表头的「全选」
只选**当前这一页**（这个项目）里没被筛掉的行。

**切换项目标签会清掉上一页的勾。** 按钮上的数字只算眼前这一页；留着别页的
勾，下次切回去一点就提交，而你早忘了勾过——勾「排队刷新」是要花钱的，
不留这种潜伏状态。要给几个项目都勾，就一个项目一个项目地来。

顶栏的筛选框跨所有项目筛，筛完每个标签上的数字变成**这个项目里命中的行数**
——筛「风控」时哪个项目中了几行，扫一眼标签条就知道，不用一页页翻。

**面板自己一个付费请求都不发**——勾上之后由 cron 在五分钟内接手，
和你在飞书里手工勾完全是同一条路，同样受 `MAX_YUAN_PER_RUN` /
`MAX_RECORDS_PER_RUN` 这些硬预算约束。

一次最多勾 200 行。面板上一个「全选」比误改一列容易得多，
而一次勾几千行就是下一轮直接顶穿预算。

**勾上之后怎么知道刷回来没有：看「最近检查」那一格的「排队中」标记。**
勾成功的行会立刻标上它（和飞书里 `排队刷新` 那个勾是同一件事的两种显示）。
标记在，这一行看到的仍是**上一次**的结论——「刷新失败」是旧的，不是这次的；
标记没了、「最近检查」变新了，才是这次刷回来的结果。cron 每五分钟一轮，
一轮里没轮到的行（预算触顶、软截止）标记会多留一轮。

**只给还在监控中的表勾。** 已停用、已移除、配置有误的表，面板会拒绝并说明
「cron 不会刷它，这几行没勾」——勾上去也没人来接，而且那些勾会悬在飞书里，
哪天一启用就集中花一笔钱。这种情况的典型来源是停用之后没等页面重载、
对着旧待办勾；现在停用会自动重载页面，一般碰不到了。

**已归档的老帖不在这个列表里**，它们折在下面单独一区。理由：
「排队刷新」会**绕过归档线**，而面板恰好把跨表的老旧异常行摆在一屏、
天然鼓励全选。那些帖子多数时候正确的处置是去飞书**取消巡查**，
不是再花钱刷一次。

### 「新」标记

自上次打开面板以来新出现的待办会标一个「新」。
「问题发现」的关键是新增，不是总量——总量天天差不多，新增才是要看的。

阅读进度存在**你自己浏览器**里，不上服务端：它是每个人自己的进度，
不是共享状态。换个浏览器或清了缓存就是全部重新标一遍，没别的影响。

## 二·四、逐表阈值

每个项目卡上有个「阈值」按钮。能改这几个：

| | 空着 = |
|---|---|
| 评估中 / 爆贴 / 大爆 的评论数门槛 | 20 / 50 / 100 |
| 无水花小时（发多久还起不来算没起来） | 48 |
| 归档天数（超过就不再自动刷） | 30 |

改完**下一轮 cron（≤5 分钟）生效，不用重新部署**。

**为什么这些可以逐表**：它们是纯行级分类，没有跨表语义，一张表改了不影响
另一张表的任何判定。而共用一套本来就是错的——美妆客户和医药客户的评论量级
差一个数量级，`config.py` 自己就写着那几个默认值「是占位的，上线前必须按
你们自己的历史数据校准一次」。

**这几个不能逐表，也不会加**：熔断比例、熔断最小样本、两击定罪次数、
冷却秒数、单轮硬预算。它们有跨表语义——`runner.apply_cross_run_breaker`
要把各表样本加总重算比例，逐表不同的熔断口径会让「这一轮到底该不该熔」
说不清。它们连列都没有，填不进来。

> ⚠️ **改阈值唯一的真实副作用**：热度档是**棘轮（只升不降）**的，改完不回溯。
> 调低门槛的行下一轮会升上去；调高门槛的行**不会降回来**，
> 于是表里会短暂并存两套口径打出来的标签。
>
> 所以保存之前先点「先算给我看」——它用表里已有的评论数算出
> 「这个项目有 N 行档位会变」，**不花钱**，还会明说哪些是「本该降但不会降」。

三档门槛必须递增（评估中 < 爆贴 < 大爆），填反了整组忽略并报出来。
超范围的值同样是报出来而不是静默忽略——静默忽略一个配置，比不支持它更糟。

## 二·五、在面板上加表删表

页面中间那块「项目」就是表清单。加表、停用、移除都在这儿，
**不用改环境变量、不用重新部署**。

### 加一张表：两条路

**A · 从零新建**（填个项目名 → 点「直接新建一张」）

应用在自己的空间里建一个多维表格，连类型带选项一次建齐。
**一次飞书都不用点**——应用自己建的 base，应用天然有完全权限。
建完链接自动填进输入框，点「体检一下」再入册。

**默认按标准业务表的结构建**（「连业务列一起建」那个勾默认是勾上的）：
照 2026-09 的「西屋」表逐列抄的——素人编号、发布时间、反馈链接、已删除评论
留底、流量状态、起量时间、笔记状态、方向、找人备注、内容配图、文案、随贴评论、
评论的素人编号、评论配图、评论状态、发布截图、相关截图、蓝词字段、蓝词图片、
作者、父记录、负面词、评论关键词、是否巡查、排队刷新、诊断信息、置顶状态、
已确认存活、巡查状态、负面状态、负面评论快照、评论区快照、实时数据.评论数、
最近检查时间、连续失败次数、平台、上次评论数——**顺序也一样**，巡查列夹在
业务列中间的位置原样保留。业务列机器完全不读不写；蓝词字段、作者这类每个
项目都不一样的词建成空的选择列，填的时候飞书自动加选项。

有两列是表建好之后**单独补**的，所以在新表里排在末尾（飞书补列只会追加），
不在西屋表里的位置——视图里拖一下就好：

- `父记录`（关联到本表）：它的配置里要填本表的 table_id，建表那一下还没有。
- `下次检查时间`：公式列，公式是运营给的原文
  `[最近检查时间] + IF(DATEDIF([发布时间], NOW(), "D") <= 2, 8, IF(DATEDIF([发布时间], NOW(), "D") <= 7, 24, 72)) / 24`
  （发布 2 天内每 8 小时、7 天内每 24 小时、之后每 72 小时——和分层刷新的
  节奏一致）。它按列名引用别的列，那些列得先存在。列名从配置取，改了列名
  公式跟着改。飞书那边可能把结果显示成数字，去列设置里把格式选成日期即可。

不勾「连业务列一起建」就退回只建巡查要用的二十来列（旧行为）。
巡查列的名字、类型、选项只有 `xhsearch/schema.py` 一份真相，模板按角色
引用它们，改列名两边不会漂。

**建完给谁开权限。** 应用自己建的表，应用是所有者——不配的话人打开只有
「可阅读」，连链接分享范围都动不了（提示「联系文档所有者 @应用名」，
一个不会回话的所有者）。运营背后的飞书账号各不相同，所以编辑权限给**群**；
管理权限给具体的人，不再全绑在机器人上。

**在面板上点出来（推荐）。**「加一张表」那个框最下面有一栏「新建的表给谁开权限」：

- **可管理**：填你的**手机号**（或邮箱、`ou_` 开头的 open_id）→「加为可管理」。
  手机号在这一步就换成飞书的 open_id 存下来（协作者接口不收手机号）——
  换不到当场报错，不会留到建表时才发现。要给应用开 `contact:user.id:readonly`
  （通过手机号或邮箱获取用户 ID）权限；填邮箱不需要这个权限。
- **群可编辑**：点「选群」→ 列出应用所在的群，勾上要开编辑权限的 → 保存。
  要给应用开 `im:chat:readonly` 权限，而且**应用得先在那个群里**
  （群设置 → 群机器人 → 添加机器人 → 搜应用名）。不在群里飞书会拒绝加群
  协作者，面板会把这个原因写在结果里。
- **给已建的表补权限**：下拉选一张已经在清单里的表 →「按上面的设置补」。
  给的是同一套人和群。应用得是那张表的所有者或可管理——自己建的表天然是。

这些选择存在注册表那个 base 里一张叫「面板设置」的小表（第一次保存时自动建），
所以**重新部署之后还在**，改了也不用碰部署。之后每一张「直接新建」的表都
自动是「你可管理、群可编辑」。

**也可以用环境变量**（部署时定死、面板上只显示不能删）：

| 变量 | 填什么 | 得到 |
|---|---|---|
| `FEISHU_TABLE_MANAGERS` | 手机号 / 邮箱 / `ou_` open_id，多个用逗号分开 | **可管理**：能改分享范围、加协作者、改结构 |
| `FEISHU_TABLE_EDITOR_CHATS` | 运营群的 chat_id（`oc_` 开头），多个用逗号分开。`python3 cli.py chats` 能列 | 群里所有人**可编辑** |
| `FEISHU_TABLE_OWNER` | 一个人的手机号 / 邮箱 / open_id（可选） | **所有权**转给这个人；应用保留可管理，照常写巡查结果 |

加协作者本身不需要额外的权限范围（`bitable:app` 就够）。一条权限没加上
不影响建表（表已经建好了，去飞书补一下比建了又建便宜），面板会逐条列出
没成的。每一次开权限都单独打一条日志（给谁、什么权限）。

**B · 接管一张已有的业务表**（粘链接 → 点「体检一下」）

体检**一分钱不花**，只读字段元数据和一行记录。它会告诉你三件事：

| 体检说什么 | 谁来做 |
|---|---|
| 「读不到这张表的字段列表」 | **只能你做**：表格右上角 `···` → 更多 → 添加文档应用 → 权限「可编辑」。开了高级权限的还要再给「可管理」 |
| 「缺 N 列，面板能建」 | 点「补齐缺的列」，面板建。`POST fields` 是纯追加，已有的列一个都不碰 |
| 「这几条要人去飞书改」 | **你做**：改错的列类型、给已有选择列补选项。理由见下 |

加进清单时**默认不启用**——体检多半还没过。确认配置齐了再点「启用」。
（默认开着的话，一张缺「最近检查时间」列的表会在下一轮 sweep 全表判到期。）

### 停用 vs 移除

- **停用**：cron 下一轮就不刷它了。可逆，随时开回来。**它只改注册表那一行，
  不碰业务表**——飞书表里那些 风控中 / 刷新失败 / 诊断信息 会原样留着，
  那是这张表最后一次巡查的结论，不是 bug。点完停用页面会按新的表清单**重载**：
  这张表的待办、卡片、KPI 里的数字一起消失，「各项目」下面留一行
  「另有 N 张表已停用：…」——停用和「读不到了」在页面上得分得开。
  全部表都停用时那一行会明说「N 张表全都停用了」，而不是「还没有一张可用的表」。
- **移除**：从清单里去掉。**只是不再监控，你飞书表里的数据一个字都不动。**
- 面板**没有**删飞书表的按钮，也不会有。那是不可逆的。

### 为什么「补选项」默认不代劳

飞书的 `PUT fields` 对 `property` 是**整体覆盖**，而选项在飞书那边是带 id 的
对象。只按名字重建一遍写回去，旧选项会被当成删除、新建，**用到它们的单元格
连值一起没**——`流量状态` 是多选、人机共用，那意味着运营手工打的标签全丢，
而且不可逆。

代码是按安全写法写的（读现值 → 带 id 原样回填 → 并集 → 硬断言新集 ⊇ 旧集，
缩集直接拒绝执行），但**「带 id 回填到底能不能保住单元格值」还没在真机上验过**。

所以：**你在一张废表上验一次，就可以永久打开它。**

```
1. 废表上建一个多选列，建两个选项 A / B
2. 填几行，分别用上 A 和 B
3. 面板上点「补齐缺的列」让它补第三个选项 C
4. 回去看那几行的 A / B 还在不在
     还在 → 设 PANEL_ALLOW_OPTION_PATCH=1，从此自动补
     没了 → 这条路封死，保持默认（面板只给清单）
```

一次性的验证，换永久的自动化。别在真表上做这个验证。

### 表清单存哪儿

一张飞书表，`python3 cli.py init-registry` 自动建好、打印一行
`FEISHU_REGISTRY=...` 粘进 Railway，**这辈子只做一次**。

它是数据库不是界面，平时不用打开。之所以选飞书表而不是别的：
面板和 cron 是 Railway 上两个**不共享任何东西**的容器（Volume 只能挂一个
服务，cron 每 5 分钟起一次跑完就退），「你点了加表」必须落到一个 cron 五分钟后
读得到的地方。而且留着「人也能进去改」是**故意的**——面板挂了的时候，
那是唯一还能止损的地方（去掉某张表的 `启用`）。

> 读不到注册表时，cron 会退回 `FEISHU_TABLES` 并**大声警告那份清单可能是旧的**；
> 两个都没有就拒跑。绝不静默跑成「零张表」——那种失败退出码是 0、
> 日志一切正常，而实际一行都没刷。

**注册表是空的时候，面板照常启动**，「各项目」那一栏会说明还没有表、
让你去下面加第一张。这条只对 `serve` 成立：刚 `init-registry` 出来的注册表
本来就是空的，而在面板上加第一张表正是它存在的理由——在这儿拒绝启动，
等于「要用面板加表，得先有表」。付费的那几条命令（`sweep` / `queue` /
`estimate`）零表照旧拒跑，那条不变量没动。

**表清单每轮刷新重读一次。** 在面板上加表/启用/停用/移除，等一轮缓存
（或点「重新取数」）就生效，不用重启面板——否则面板和 cron 会长期显示
不同的在管清单，而面板正是用来看这件事的。

### 余额：看它不花钱

面板上有一块显示两家数据通道的余额，以及**按最近几轮的实际花速算出来的
「还够跑几天」**。后者才是运营真正想知道的那个数——「还剩 ¥400」要人自己
心算，而心算的前提是知道每天花多少，那正是没人知道的。

**这一块没有破坏「面板不发付费请求」那条不变量**，因为两家的余额查询端点都是
它们自己机器可读的定义里标明零费用的：

| 通道 | 端点 | 零费用的出处 | 对照：我们真正在花钱的那个 |
|---|---|---|---|
| TikHub | `/api/v1/tikhub/user/get_user_info` | 计价表 `endpoint_cost: 0.0`（`get_all_endpoints_info`，免鉴权就能查） | `get_note_comments` = `0.01` |
| SocialDataX | `/socialdatax/api/v1/points/balance` | OpenAPI `x-socialdatax-cost-points: 0`、`"余额查询不扣积分。"` | 评论端点 = `10` 积分 |

代码上这条线是**单独关起来**的：`xhsearch/balance.py` 不 import
`providers` / `runner` / `protocol`，只认 `FREE_ENDPOINTS` 里那两条路径，
有 AST 测试钉死它拼不出别的地址、面板也不许绕过它直接碰 `transport`。
不这么做的话，余额查询就会顺手蹭付费端点的那根请求管道，以后谁改一行都可能漏过去。

价格会变。哪天这两个端点开始收费，`balance.py` 开头那张表和 `FREE_CHECKED_ON`
就是发现它的线索。

**读不到就说读不到，绝不显示 ¥0。** 真的余额为 0 和读不到余额，要人做的事
完全相反（一个去充值，一个去查 Key），而 ¥0 长得像前者——这和「缺列时
estimate 报 ¥0.00」是同一类错误。一家读不到不影响另一家，两个账户是独立的。

「还够跑几天」有两道下限：至少 3 轮、至少覆盖 2 小时，否则只报「样本不够」。
一轮恰好赶上批量勾排队刷新，算出来的日花速能比真实高一个数量级，
据此说「只够跑 2 天」会让人白白去充一笔钱。

运行历史里还多一列「跑完剩」——那个数**一个额外请求都没发**：SocialDataX
每次付费响应本来就带 `points.balance`，`runner` 早就写进 `run_end` 事件了，
面板只是把它捞出来。它是「花完这一轮之后」的真实读数，比任何时点查询都更贴近
「这一轮花掉了多少」。

### 视觉：BYWOOD 设计系统 v5.4.0（色板 v5.1）· 界面轨「管理后台」

面板按品牌准则做过一版，遵的是 `bywood-design-system` 的**界面轨 · 场景 03
（管理后台）**：侧栏 240 + 顶栏 56 + 内容区 24 / max 1440，KPI 行 1 个深青
主块 + 最多 3 张白卡，表格表头 44 / 行 48 / 发丝线分隔 / 无斑马纹，
徽标语义浅底 + 加深档文字，直角制度、零阴影、零渐变、零毛玻璃。

v5 是一次**品牌换届**（「青赭双色制」）：标志由「双箭分发」换成「山形」，
主色深青接动作与结构，强调色赭石 `#B8502F` 接旧品牌红的
「价值与增长」全部角色；双箭图形语言连同它的链接尾标 `»` 整体退役。
版式零变更——变的是品牌层，不是骨架。跟着换届来的还有两条实现细节：
token 一律按角色命名不按色相（`--tint-sky` 改叫 `--tint-primary`，
下次换色只改值不改名），深色模式主按钮是**亮青底 + 墨字**
（亮青上白字只有 2.11:1），靠 `--on-primary` 这个 token 翻转实现，
组件代码仍然只有一套颜色。

色板 v5.1（2026-09-02）是一次**「标志青回归」**：v5.0 的主色 `#1C4F62`
取自标志渐变的冷端（H196°），比标志实心青偏蓝 19°，整套读成深湖蓝。
v5.1 把主色收回到标志本体色相的深档 **`#1E5754`**（白底 8.25:1），
深色模式主色改渐变暖端 `#6AC1BD`（深底 8.85:1）。token 一个没改名，
只改值——这正是 v5 「角色命名」当初要换来的东西。同时标志青 `#7ED1CD`
由「只能出现在标志里」放开为**品牌面色**：做底不做字，块内只放墨字或
主色字，每屏 ≤1 块。本面板只在**登录页**开这一块（登录页是品牌时刻）：
青底 · 墨字 · 墨版山形，加一句这个面板的判断「面板负责发现，飞书负责处理」；
后台那一屏是工作层，不开青面。

**色值全部来自 `tokens/palette.json` 的 `screen` 节。** 这里没有引设计系统的
`tokens/globals.css`——那是 Tailwind 的 `@theme`，而这个面板是零依赖的
标准库 `http.server` 手拼 HTML，引不进来。所以是**照着同一份事实源手写同名
CSS 变量**，角色和取值一一对应。改色板要两处同改，`tests/test_design.py`
里那份副本会在不一致时红。

几个和上一版不一样、且有理由的地方：

- **顶栏那排数字改成了 1 主 3 副。** 上一版是 6–7 个同规格方块排排坐，
  正是负面清单 #9 点名的形态——数字一样多，但没有主次，眼睛落不到
  「今天该干什么」上。主块给「要人管」，那是这个面板存在的理由。
- **原来那排里的在管行数 / 排队中，降成了标题下的一行编辑式导语。**
  它们是背景信息，不是决策点。
- **emoji 换成了 lucide 线性图标**（负面清单 #1），内联 SVG——CSP 是
  `default-src 'none'`，而且这个项目零依赖，外链和图标字体都不行。
  ⚠️ 服务端日志里的 emoji 没动：那是运维文本，不是界面。
- **深色模式只翻 token**，组件代码没有第二套颜色。
- **四态齐了**：正常 / 骨架（第一次取数、异步拉项目清单）/ 空 / 出错。
- **双箭退役了**（v5 换标）。链接尾标「打开这张表 »」的 `»` 摘掉，
  链接可辨识性交给赭石色 + 下划线悬停态；区块层级交给字重与深青字色。
  标志换成山形 mark（几何逐字取自 `logo/elements/bywood-mark-current.svg`，
  currentColor 浅底深青、深底白、青面上墨——独立山形在浅底不用标志主青，
  白底 1.77:1，没有词标兜底就是一团雾）。
- **表格行操作是 13px 主色深青**，不是通用的 accent 赭石。`scenarios/03`
  明写「行操作用 13px 蓝字链接」，而模板里通用的 `a` 是赭——仲裁顺序里
  **场景文件规则高于可执行模板**，这一处听场景的。理由在屏幕上也看得出来：
  赭石是留给「价值与增长」的，每一行都挂一个暖色链接会和真正的
  告警徽标抢眼睛。
- **数字和中文量词之间留一个空格**（`9 天` / `20 条`），跟模板一致。
- **深浅模式有手动开关**（模板同款）：右下角悬浮月亮按钮，默认跟随系统，
  点一下从「当前生效的」翻走并存进 localStorage——那是每个人自己的偏好，
  不上服务端。实现仍是 token 翻转：按钮只设 `<html data-theme>`，
  组件颜色零改动。

自检怎么跑：

```bash
# 仓库自带的（CI 会跑）
python3 -m unittest tests.test_design

# 设计系统自带的机器闸（要有那个包）
python3 -c "…渲染一份 HTML 出来…" > /tmp/panel.html
python3 <设计系统包>/tools/check-design.py /tmp/panel.html
```

两个是互补的：机器闸管全轨通用的六条（色板 / 圆角 / 阴影 / 渐变 / 毛玻璃 /
对比度），`tests/test_design.py` 管那六条**加上**这一轨特有的构件上限
（KPI 组成、侧栏激活态、无斑马纹、金额带 `num`）。机器闸住在设计系统包里、
CI 上够不着，所以最容易踩回去的那几条在仓库里也钉一份。

**改完看渲染截图做眯眼测试，别只看代码。** 这一版就是靠截图抓到两个机器闸
查不出来的错：品牌双箭因为 CSS 转义写成了 `\\00bb`（多一个反斜杠）在页面上
渲染成字面量，以及一张只有一行错误的项目卡被网格拉成和邻居等高、中间空出
几百像素。

### 🚨 Railway token 的选型是个安全决定

同一套 GraphQL 上有 `variables` 查询（已核实存在）。也就是说**一个能读日志的
account / workspace token，同样能读回这个项目的全部环境变量**——
`TIKHUB_API_KEY`、`SOCIALDATAX_API_KEY`、`FEISHU_APP_SECRET` 全在里面。

用一把能解开所有密钥的钥匙，去换一段日志摘要，这笔交换不一定划算。按这个顺序选：

1. **project token**（`RAILWAY_PROJECT_TOKEN`）—— 范围限于一个项目的一个环境，
   走 `Project-Access-Token` 头。两个都配时代码用这个。
   ⚠️ 它能不能读 `environmentLogs` **还没实测过**，这是上线前要验的一条。
2. 读不了才退回 `RAILWAY_API_TOKEN`，而且请建在**面板服务的服务级**变量里，
   不要建项目级（cron 那个服务根本不需要它）。
3. 实在不放心就整块不配。**面板九成的价值不在日志那一块**，
   跨表待办列表照常工作。

### ⚠️ 面板服务上不要配上游 Key

`TIKHUB_API_KEY` / `SOCIALDATAX_API_KEY` **不要**配在面板服务上。
它一个付费请求都不发，配上只是让公网那一侧多两份密钥。
日志里的 Key 由 cron 那边在打印之前就脱掉了（`providers._redact`），
不依赖面板再脱一次。

代价只有一个：面板报的「预计花费」会按**配置的主通道**计价，而不是
「第一家真配了 Key 的」——只配备胎 Key 的部署下那个数会偏。

飞书凭据、表清单、判定口径全部沿用 cron 那一套（`FEISHU_APP_ID` / `FEISHU_TABLES` / …），
**两边同一份配置**，口径不会打架。

### 为什么评论正文默认不显示

`评论区快照` 和 `负面评论快照` 里有**别人写的评论正文、昵称和 IP 属地**，
是个人信息。面板对运营开放、又挂在公网上，默认展示等于把暴露面放大一圈。

运营需要的「发生了什么、去哪查」由机器写的 `诊断信息` 那一列和直达链接满足，
那一列不含个人信息。要看内容，点进飞书看。

法务过完再 `PANEL_SHOW_DIGEST=1`。

## 四、部署（Railway 第二个服务）

在**同一个 Railway 项目**里 `New Service` → 选同一个仓库：

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py serve` |
| Cron Schedule | **留空** |
| Restart Policy | `On Failure`（这个是常驻服务，跟 cron 那个相反） |
| Networking | `Generate Domain`，拿到一个公网地址 |
| Health Check Path | `/healthz` |

项目级变量（飞书凭据、表清单）自动共享，只要再加 `PANEL_PASSWORD` 和 `FEISHU_DOMAIN`。

### ⚠️ 两条不能踩的线

1. **面板服务绝不能配 Cron Schedule。**
2. **面板服务的 Start Command 里绝不能出现 `queue` 或 `sweep`。**

理由是同一条：两个容器同时刷同一张表 = 钱花两份 + 人工标签被旧快照覆盖 +
飞书 `1254291` 写冲突。`xhsearch/runlock.py` 是**文件锁**，两个容器各有各的
文件系统，它拦不住这个拓扑。**付费执行者永远只能有 cron 那一个。**

代码这边也上了闸：`xhsearch/panel.py` 不 import 供应商那一层、不调任何会发
付费请求的函数，有测试按 AST 逐个调用节点检查。

### 花多少钱

常驻进程按分钟计费，约 **$0.3–1/月**（cron 那个是 $0.1）。
相对数据接口的 ¥950/月，这是噪声。

## 五、安全上做了什么、没做什么

用的是 Python 标准库的 `http.server`，为的是守住这个项目的零依赖。
它的文档自己写着 **"not recommended for production, it only implements
basic security checks"**，所以代价逐条堵掉了：

| 文档点名的风险 | 怎么堵的 |
|---|---|
| `SimpleHTTPRequestHandler` 跟符号链接、能读到目录外的文件 | 完全不用它。面板不从磁盘 serve 任何东西 |
| `send_header()` 不校验 CRLF，可被头注入 | 响应头全是写死的常量，没有把用户输入放进头的路径 |
| 没有 body 上限 | 按 `Content-Length` 卡 64 KiB，**先拒再读** |
| 没有超时 | socket 有超时，线程是 daemon |
| Python 3.11 不清洗日志里的控制字符（3.12 才修） | 自己清洗，见 `_sanitize_for_log` |
| XSS | 飞书来的文本一律 `html.escape`；CSP `default-src 'none'`，只额外放 `connect-src 'self'`（页面要 fetch 自己的接口）、内联样式与内联脚本。外部脚本、外部样式、远程图片全部不许 |

另外：口令常量时间比较、会话 Cookie 走 HMAC 签名 + `HttpOnly` + `SameSite=Strict`、
非 GET 请求要带 `X-Panel-Token` 头（跨站请求带不上它）、登录失败按来源限速
（不做全局锁定——那意味着任何人都能让整个团队登不进来）。

`Secure` 属性只在**能确定是明文 localhost** 时才去掉，好让本地开发能登进去；
判断不出来一律加上，失败方向是「更严」。

**没做的**：要给更大范围的人用，正确做法是前面放 nginx/Caddy。
那会打破零依赖，所以现在不做——但这个取舍写在这里，不是等出事了才发现。

## 六、本地跑一下

```bash
set -a && source .env && set +a
PANEL_PASSWORD=local-dev-passphrase PORT=8080 FEISHU_DOMAIN=https://xxx.feishu.cn \
  python3 cli.py serve
```

浏览器开 <http://localhost:8080>。

**验它没花钱**：看「运行历史」那两列——**相邻两轮的「跑完剩」之差，
必须正好等于后一轮的「花费」**。面板在这两轮之间刷了 4–5 次，它要是花了一分钱
这个差就对不上。

（别用「起面板前后余额不变」当判据：cron 每 5 分钟就在花钱，余额一直在掉，
那个条件永远不成立。这是文档里写错过一次的地方，见 `待验证清单.md` 17c。）

**验数字对**：面板上的「到期待刷 N 行 ≈ ¥X」和 `python3 cli.py estimate`
的输出应该逐字相同——两边走的是同一个 `rows.estimate_yuan`。
