## 一、阻断级：不验完不要上生产

### 1. ⚠️ 各错误码对应的真实业务场景

**好消息：错误码本身不用猜了。** SocialDataX 有一份**公开可读、不需要 Key 的
OpenAPI 3.1 规范**，里面带完整的错误码契约：

```bash
curl -sS https://api.52choujiang.cn/socialdatax/api/v1/docs/openapi.json \
  | python3 -c "import json,sys; print(json.dumps(json.load(sys.stdin)['x-socialdatax-error-contract'], ensure_ascii=False, indent=1))"
```

`protocol.py` 里的 `_CODES` 就是照它写的，**不是猜的**。

**还要验的是映射**：规范给了错误码的定义，但没说「小红书笔记被删」实际会命中
`1003 not_found` 还是 `1006 content_unavailable` 还是 `1008 content_deleted`。
这三个在代码里的处置不同：

- `1003` / `1006` → 走两击定罪（连续两次才判失效）
- `1008` → **权威结论，第一次就定罪**（规范原文「作为业务失败处理，不要重试」）

映射错了的后果：把 `1008` 当成 `1003` 只是晚一轮发现，可以接受；
反过来把某个瞬时故障当成 `1008` 就会误杀。

**怎么验**：找 3 条已知被删的小红书笔记 + 2 条私密/受限的 + 各 2 条抖音同类，
各调一次，记下真实返回的 `code`：

```bash
export SOCIALDATAX_API_KEY=sk-xxx
curl -sS -X POST https://mcp.socialdatax.com/socialdatax/api/v1/xhs/note/comment/list \
  -H "Authorization: Bearer $SOCIALDATAX_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"note_id":"<一条已删笔记的ID>","sort_type":"default"}'
```

成本：约 ¥1（如果失败调用不扣费，则为 ¥0，见第 6 项）。

### 2. ⚠️ 成功响应的确切字段

响应字段名已从 OpenAPI 规范核对过（与 MCP schema 完全一致，同一个后端）。
但**没有见过一次真实的成功响应**。

**怎么验**：拿真 Key 对一条正常笔记调一次，把整个 JSON 打出来，
确认 `items[].is_pinned`、`comment_count`、`points.cost` 都在。成本 ¥0.10。

### 3. ⚠️ 评论第一页实际返回几条

官网只说「每页约 10-20 条」，接口没有 `page_size` 参数，输出里也不返回页大小。

对「前 5-10 条」这个需求无风险（10 条和 20 条都是一页、一个价），
但如果实际是 10 条，`DigestFormat.max_comments = 8` 就刚好；如果是 20 条，
可以调大到 12–15，**不额外花钱**，氛围判断质量明显更好。

**怎么验**：各平台跑 3 条不同热度的内容，数 `items` 长度。成本 ¥0.60。

## 二、影响成本模型

### 4. ⚠️ 「最多 3 并发」是服务端限流还是行为建议

这句话出现在 SocialDataX 官方 skill 文档里，但那是**给 agent 的行为约束**，
不等于服务端阈值。`config.py` 里保守设成 2。

**怎么验**：用 6 并发打 12 次，看是否出现 `rate_limited`。
如果服务端宽松，批量窗口能显著压缩。成本 ¥1.20。

### 5. ⚠️ 抖音 `comment_count` 返回 null 的实际频率

schema 写的是 `integer|null`，实际频率未知。目前代码对抖音**恒定**补一次 detail，
抖音单条成本因此是小红书的两倍。

**怎么验**：抽 20–30 条抖音作品跑一遍，数 null 率。如果接近 0%，
可以改成「只在 null 时才补 detail」，抖音侧预算直接砍半。成本 ¥2–3。

### 6. ⚠️ 失败调用是否扣积分

只有蒲公英工具明确写了「失败不扣费」，其余接口无明文。影响重试策略的成本。

**怎么验**：验第 1 项时，对比调用前后的 `points.balance`。成本 ¥0。

### 6b. ✅ 限流响应的字段名（已解决）

不用验了。OpenAPI 规范明确：HTTP 429 时 body 带 `retry_after_seconds`、
`rate_limit_max_requests`、`rate_limit_window_seconds`、`rate_limit_requests_per_second`，
同时响应头带 `Retry-After`。代码里用的就是 `retry_after_seconds`。

### 7. ⚠️ `sort_type: "default"` 是不是 App 里的「综合」序

枚举是 `[default, time_descending, like_count_descending]`，默认值 `default`，
但没有一处文档说 `default` = App 里的综合排序。这关系到「前 8 条评论」的口径。

**怎么验**：同一条笔记，API 返回的前 8 条 vs App 里综合序前 8 条，肉眼比对。成本 ¥0.10。

### 8. ⚠️ 小红书 `comment_count` 是否等于 App 上显示的评论数

schema 说它「含一级评论与回复」。App 上显示的可能是另一个口径。
运营一定会拿这个数和 App 对账，对不上就会来问。

**怎么验**：3 条笔记逐个比对。如果对不上，改用 `top_level_comment_count`
并在 `诊断信息` 里注明口径。成本 ¥0.30。

### 8b. 💡 评论接口能不能看出「蓝词」（词变成了超链接）——未来能力

蓝词目前是人工手机端自查的（小红书只有手机端能看到，抖音手机端和网页端
都能看到），机器对「蓝词字段」不读不写。**如果**评论接口的原始响应里带
超链接标记（抖音评论有 `text_extra` 一类的富文本结构，小红书未知），
蓝词检测就能自动化，「蓝词字段」才能和监控打通。

**怎么验**：找一条已确认出蓝词的评论，调一次评论接口，看原始 JSON 里
那个词的位置有没有链接/高亮标记。TikHub 是上游透传，值得一试。
成本 ¥0.01–0.10。验证之前**不做**任何蓝词自动判定——凭没验过的字段
下结论，正是这套系统最不能犯的错。

## 三、飞书侧

### 9. ⚠️ 你们的套餐有多少自动化运行次数

各版本从 200 次/月到 50 万次/月不等，**按租户共享，自动化和工作流共用**。

这决定按钮字段能不能用：如果只有 200 次/月，按钮点几百次就会把全公司的自动化额度打光，
且失败模式是**静默停摆**（表不报错，只是不更新）。

**怎么查**：飞书管理后台 → 企业管理 → 费用中心 → 权益数据。

低档位的应对：**别建按钮字段，只用「排队刷新」复选框 + 后台轮询**，一次配额都不消耗。

### 10. ⚠️ 写入不存在的多选选项会怎样

记录 API 的文档说会**自动新建选项**，但 `batch_update` 是全成功或全失败，
一个拼错的标签可能让整批几百行一起回滚。

代码里用 `known_options` 做了过滤（读字段配置，只写已存在的选项）。

**怎么验**：手动调一次 API 写个 `测试标签X`，看字段配置有没有多出一项。
**无论结果如何，上线前把五个机器标签在字段里预建好。**

### 11. ⚠️ 多选字段是不是真的是「多选」类型

如果你们的 `流量状态` 实际是**单选**，「加标签不覆盖」这个需求在技术上根本不成立，
必须先改字段类型，或者另开一个多选列给机器写。

**怎么验**：`python3 cli.py doctor` 会打印这个字段的选项列表；
读不到就是权限问题，读到了但类型不对要去飞书里看。

文档说代码节点支持任意 HTTP/HTTPS（内置 `requests_async`），但**没有对第三方域名实测过**，

**两个域名都要验**——双通道的价值就在于不把命押在一家上，但如果扣子只通其中一个，

**这两条都不通，整个扣子方案立刻作废**，要转成独立服务。

**怎么验**：建一个只有 1 个代码节点的工作流，用**假 Key** 打一次：
返回 **401** 说明网络通了（抵达了业务层）；超时或连接错说明出网受限。成本 ¥0。
探测代码见 git 历史里的 `docs/扣子工作流搭建说明.md` 第五节（文件已随扣子路径移除）。

### 12b. ⚠️ 扣子的 `requests_async` 发出去的 UA 会不会被 Cloudflare 拦

TikHub 挂在 Cloudflare 后面，实测裸 urllib 的 UA 直接 403（`error_code 1010`）。
代码里写死了浏览器 UA，但**扣子的 `requests_async` 允不允许覆盖 `User-Agent` 请求头，
没有文档保证**。

第 12 项的探测如果对 tikhub 返回 403 + `error_code 1010`（而不是 401），
就是撞上这一条了。那种情况下扣子上的 TikHub 通道用不了，只能走 SocialDataX。

### 13. ⚠️ `requests_async` 的 `response.text` 和 `response.headers` 行为

代码里要读三样：`response.text`（body）、`response.status_code`、
`response.headers['x-request-id']`。扣子文档没写 `requests_async` 的响应对象长什么样。

**怎么验**：验第 12 项时顺手 `print(response.status_code, len(response.text))`
和 `print(dict(response.headers))`。取不到 headers 也不致命——
代码里包了 try/except，request_id 会退化成空串。成本 ¥0。

### 14. ⚠️ 扣子定时触发器在你们套餐上是否可用

文档确认最小间隔 1 分钟、支持 cron，但没确认免费版是否开放。

**怎么验**：建一个每分钟触发的空工作流，等 3 分钟看运行记录。

## 五、TikHub 通道剩下没验的

主体已实测（置顶字段、失效信号、计费、脱敏、Cloudflare、大陆域名——见
[`供应商对比.md`](供应商对比.md)）。剩下四条：

### 15. ⚠️ 余额耗尽时到底返回什么

TikHub **没有公开的业务错误码表**（SocialDataX 有）。现在靠 HTTP 402/403 +
「余额 / 充值 / insufficient / balance」文案兜。归错的后果是不会降级到备胎，
白白让一整轮跑空。

**怎么验**：等余额真的见底那次，把响应记下来贴进 `_TIKHUB_HINTS`。
或者建一个只充极少钱的测试 Key 打空它。成本 ≈ 余额本身。

### 16. ⚠️ `in_censor` / `is_prohibited` / `in_reviewing` 在真被封的帖子上是不是 true

只见过 `false`。**运营已拍板把它提升成判定依据**（2026-08）：返回 True 就打
「风控中」——风控中只认两种硬证据（审查标记、链接失效），评论数异常一律走
疑似限流/无水花。因为字段语义仍没在真被封的帖子上实测过，打标签的同时
诊断信息里保留「请人工确认」，误报窗口靠人工兜住。

**怎么验**：拿 2–3 条你们自己确认被限流/被封的笔记调一次 detail，看这个字段。
成本 ¥0.15。验实之后可以把诊断里的「请人工确认」去掉。

### 17. ⚠️ 空壳判活的启发式会不会误伤

不存在的笔记返回的空壳，和「真实存在但零评论的新笔记」只差
`user_id` 和 `all_sort_strategies` 两个字段。我们赌的是**活笔记一定带作者 id**。

**怎么验**：找一条刚发布、确实零评论的自己家笔记调一次，确认 `user_id` 非空。
成本 ¥0.07。这条没验的风险被两击定罪 + 全局熔断挡着，不是阻断级，但值得顺手验掉。

### 17b. ✅ TikHub 余额的单位是美元（2026-08-26 使用者确认）

`get_user_info` 返回的 `user_data.balance` 单位是**美元**，和计价表里的
`endpoint_cost` 同一单位。面板按 `USD_TO_CNY`（默认 7.2）折成人民币，
原值和折算值**并排显示**——汇率是我们自己配的，会漂；原值不会。

`free_credit`（赠送额度）**没算进**余额，也没算进「还够跑多久」。
宁可低报：把赠送额度算进去会让「还够跑 N 天」偏乐观，而这个数存在的
意义就是提前提醒充值。要改成算进去，改 `balance.read_tikhub` 一行。

### 17c. ✅ 两个余额端点是零费用（已按官方定义核实，2026-08-26）

- TikHub `/api/v1/tikhub/user/get_user_info` → 计价表 `endpoint_cost: 0.0`
  （`get_all_endpoints_info` 免鉴权就能查，对照 `get_note_comments` 是 `0.01`）
- SocialDataX `/socialdatax/api/v1/points/balance` → OpenAPI
  `x-socialdatax-cost-points: 0`，`x-socialdatax-billing-description:
  "余额查询不扣积分。"`（对照评论端点是 `10` 积分）

**真机上怎么确认（这一条上一版写错了，2026-08-26 改）**

原来写的是「起面板前记下余额，刷十几轮后再对，一分不差」。**那个判据不成立**：
cron 每 5 分钟就在花钱，余额本来就一直在掉，「一分不差」永远不会发生。
拿它当证据只会得出「面板在花钱」的假结论。

正确的判据在**已经有的数据**里，而且更严：

> SocialDataX 每次付费响应都带 `points.balance`，收尾事件同时记着那一轮的
> `cost_yuan`。**相邻两轮的余额差，必须正好等于后一轮的花费。**
> 面板在这两轮之间刷了 4–5 次——它要是花了一分钱，这个差就对不上。

面板的「运行历史」把这两列并排放着（`花费` 和 `跑完剩`），一眼就能对。
不用记基线、不用开后台。

> ⚠️ **两列口径不同，别直接减。** `花费` 是两家通道加起来的合计，
> `跑完剩` 只反映 SocialDataX 的积分余额。所以这条等式只在**全走
> SocialDataX 的那一轮**成立——结果徽标后面没有「降级 N 次」小标的那种。
> 混走两家的轮子，余额差只会等于花费里 SocialDataX 那一部分。

> ⚠️ **2026-08-27 之前这条根本做不了。** `points_balance` 是 runner 在
> **表级**事件里发的，而 `railway.py` 只从 `run_end` 读、`cli.py` 发
> `run_end` 时又没带它——三处对不上，「跑完剩」那一列永远是「—」。
> 测试没拦住是因为断言全落在 `report.points_balance` 这个内存对象上，
> 没有一条走过「日志 → Run」这段解析。现在两边都修了：收尾事件补发它，
> 解析端读不到时从表级事件取最小的那个（宁可低报）。

TikHub 那边响应里不带余额，没有同样的被动信号。它的闭环是另一件事：
**面板显示的 `$xx.xx` 和 TikHub 后台对一眼**——那同时也确认了单位和汇率
折算没错（见 17b）。一次就够。

价格会变。`balance.FREE_CHECKED_ON` 是上次核对的日期，
`tools/probe_endpoint.py` 那套 401/404 判据同样适用于重新核实。

### 18. ⚠️ 抖音评论的 `label_type` / `label_text` 是不是置顶

抖音评论条目里有这两个字段（SocialDataX 那边没有），但语义没验过。
**现在一律不判置顶**，和当初的承诺一致。

**怎么验**：找一条有置顶评论的抖音视频调一次，看第一条的 `label_type` / `label_text`。
成本 ¥0.007。如果真是置顶，抖音也能做置顶监控了——那是白捡的能力。

- ✅ REST 端点 `https://mcp.socialdatax.com/socialdatax/api/v1/...`，纯 JSON，请求体就是参数本身
- ✅ 鉴权：`Authorization: Bearer <KEY>` **或** `X-API-Key: <KEY>`，**只能用一种**，同时传判为配置冲突
- ✅ **业务错误也返回 HTTP 200**，靠 body 里有没有 `code` 字段区分。
  规范原文：「请求成功；业务错误也会返回 200 + {code, message}。」
  成功响应不带 `code`（「成功响应不会返回该字段」）
- ✅ 无 Authorization → HTTP 401 `{"code":1401,"message":"API Key 缺失，请通过 Authorization 或 X-API-Key 传入。"}`
- ✅ Bearer 无效 → HTTP 401 `{"code":1401,"message":"API Key 无效或已失效。"}`
- ✅ 响应头带 `x-request-id`，找厂商排查的唯一凭据（代码里会写进「诊断信息」列）

### 数据能力

- ✅ 小红书评论 `sort_type` 枚举 `[default, time_descending, like_count_descending]`，默认 `default`

### MCP 端点（本项目改用 REST 后不再走这条路，但仓库里的 8 个 skill 仍在用）

- ✅ `https://mcp.socialdatax.com/{platform}/mcp`，JSON-RPC over HTTP，无状态
- ✅ `Accept` 必须同时含 `application/json` 和 `text/event-stream`，少一个硬报 **HTTP 406**
- ✅ 成功响应是 SSE 分帧，错误响应是纯 JSON —— 同一接口两种 content-type

> 这也是**飞书自动化的 HTTP 节点没法直接打 MCP 端点**的原因：它按「粘一段 JSON 样例」
> 解析响应，喂 SSE 进去解不出来。REST 端点没有这个问题（纯 JSON），
> 但飞书仍然无法从数组里取出置顶那条评论，所以中间层依然必需。
