# 多维表格全量设置说明（OKMAN 系列表对齐版）

这份文档回答两个问题：**每一列叫什么**、**每一列内部怎么配**。
列名对了只是表面——字段类型、选项清单这些「内在配置」不对，机器照样
读不到或写不进。`python3 cli.py doctor` 会按本文档的口径做全量体检
（列在不在、类型对不对、选项建没建），建完表先跑一遍 doctor 再开跑。

三条铁律：

1. **列名逐字相同**：与 `xhsearch/config.py` 里的 `FieldNames` 一字不差
   （含空格、括号全半角、英文点号——`实时数据.评论数` 里那个点也是列名的
   一部分）。飞书按字段名寻址，对不上直接报 `1254045 FieldNameNotFound`。
2. **字段类型按下表建**：类型不对的典型翻车——`最近检查时间` 建成了系统的
   「最后更新时间」类型（机器写不进去，且任何人工编辑都会刷新它，分层刷新
   全乱）；`流量状态` 建成单选、或 `评论状态`/`负面状态`/`置顶状态` 建成多选
   （写法与类型错配——前者按多选列表合并写，后三者按单选字符串覆盖写）。
   这类错配飞书会报 `1254063 MultiSelectFieldConvFail`。
3. **机器要写的选择值先建选项**：没建的选项会被自动拦下（不会写坏表），
   但对应的判定就等于没生效。

你们已有的业务列（素人编号、方向、文案、随贴评论、曝光量……）机器
**完全不读不写**，随便加减。下面只列机器要用的列。

> 表里还没建的机器列会被**自动跳过**（不会写坏表、不会整批回滚），跳过的
> 列名会打在运行日志里。**类型建错的列同样只摘掉它自己**：写回前会拿字段
> 类型逐列核对一遍值的形状，对不上的单独跳过，其余列照常落表——否则一列
> 建错就能让整张表这一轮已经付过钱的结果全部作废（`1254063`）。日志里
> 会写清是哪一列、现在建成了什么、应该是什么。

跳过归跳过，那一列的数据就是没落下来。**看到这段提示就去把类型改对**，
不改的话它每一轮都落不下来，而钱每一轮都在花。掉了列的那一轮退出码是
非零，cron / Actions 会显示失败——这是故意的，否则它会一直安静地花钱。

> 🚨 **`最近检查时间` 和 `排队刷新` 是例外，它们不走「跳过」这条路。**
> 别的列写不进去只是少一列数据；这两列写不进去会**循环烧钱**——刷过的行
> `最近检查时间` 没推进，下一轮 sweep 照样判它到期，于是每一轮都重新付费
> 刷同一批行；勾选清不掉的话 queue 模式同理。所以这两列的类型不对时，
> `sweep` 和 `queue` 在**花钱之前**就拒跑（`row` 模式是人工点名要数据，
> 照跑但会警告）。

## 〇、「蓝词字段」：机器不碰，此列与本系统无关

**蓝词**（评论里变成搜索超链接的词）是人工在手机端自查的——小红书只有
手机端能看到蓝词，抖音手机端和网页端都能看到。目前接口数据里拿不到
「这个词有没有变成超链接」，所以机器**不读不写**这一列，它和下面的
「评论关键词」是两回事：

| | 蓝词字段 | 评论关键词 |
|---|---|---|
| 查什么 | 词有没有变成蓝词（超链接） | 我们的种子评论有没有显示出来 |
| 谁来查 | 人工（手机端目检） | 机器（每轮自动匹配第一页评论） |
| 结果落在哪 | 人工记录 | `评论状态` 单选 + 快照第一行的「命中」标记 |

（若将来验证出评论接口能带回超链接标记，蓝词检测可以自动化——
见 `docs/待验证清单.md`。）

## 一、人工维护的列

| 列名 | 字段类型 | 必填 | 内在配置与说明 |
|---|---|:---:|---|
| `反馈链接` | **文本** | ✅ | 原样粘贴分享文案或链接（`xhslink.com` 短链直接可用）。**不要建成「超链接」字段**——它会规范化链接，可能吞掉小红书短链里的 token |
| `发布时间` | **日期** | 建议 | 要手填的普通日期字段，**别用「创建时间」类型**（那是建行时间，不是发布时间）。分层刷新靠它分档；留空的行每轮都刷（宁可多花一毛，也别让一行永远不更新） |
| `评论关键词` | **多选 或 文本** | 选填 | 一组词（如 `西地那非口溶膜`、`艾时达口溶膜`、`cGMP因子`），任一词出现在第一页任一条评论里 = 我们的评论显示出来了。多选列直接建选项；文本列用 顿号/逗号/分号/换行 分隔。匹配不区分大小写、忽略空白和标点（`cGMP因子`/`cgmp 因子` 都能中）。**没填这一列的行，机器不碰 `评论状态`** |
| `负面词` | **多选 或 文本** | 选填 | 一组**负面词 + 竞品词**（如 `过敏`、`踩雷`、`智商税`、竞品品牌名），格式和匹配规则与 `评论关键词` 完全一样。方向正好相反：`评论关键词` 查**我们自己种的评论显示了没有**（希望命中），这一列查**别人在底下说了什么**（不希望命中）。**没填这一列的行，机器不碰 `负面状态` 和 `负面评论快照`** |
| `是否巡查` | **复选框** | ✅ | 勾上才刷新；取消勾选即完全停止。结案后勾掉，永久止损 |
| `排队刷新` | **复选框** | ✅ | **手动触发入口**。勾上 → 后台处理 → 自动清掉，勾消失就是「已完成」。可拖拽批量勾，90 秒内连勾多次只算一次 |

> 为什么手动入口用复选框而不是按钮字段：复选框走后台轮询，**一次飞书自动化
> 配额都不消耗**，而且能拖拽批量勾 50 行。按钮每点一次消耗一次租户级配额。

## 二、机器写入的列

| 列名 | 字段类型 | 内在配置与说明 |
|---|---|---|
| `平台` | **单选 或 文本** | 单选时先建好两个选项：`小红书`、`抖音`。机器按链接域名识别 |
| `实时数据.评论数` | **数字** | 含回复的总评论数。格式选「整数」即可 |
| `上次评论数` | **数字** | 写新值前先搬过来，公式列算增量用。建议隐藏 |
| `置顶状态` | **单选**（三个选项见下） | **我们的置顶还在不在**：`置顶成功` / `置顶掉了` / `无置顶`，机器直接覆盖。只记状态不记内容（置顶那条的内容在快照里照常能看到，排最前）。抖音接口没有置顶字段，**抖音行不写这一列** |
| `评论状态` | **单选**（两个选项见下） | **由关键词命中驱动，直接覆盖当前值**：命中=`显示评论`，未命中=`没有显示`（`待评论` 等人工旧值会被结论覆盖——单选只显示当前状态） |
| `评论区快照` | **文本** | 综合排序前 8 条评论。**命中关键词的那条排第一行并带「命中『词』」标记**，然后是置顶那条，其余接后——一列同时回答「显示了吗、显示的是哪条、评论区什么氛围」 |
| `负面状态` | **单选**（两个选项见下） | **由 `负面词` 命中驱动，直接覆盖当前值**：命中=`有负面`，没命中=`无负面`。用的是**和 `评论状态` 同一份第一页评论**，不额外发请求、不翻页——多这一列不多花一分钱 |
| `负面评论快照` | **文本** | 只放命中负面词的那几条，每条标出命中的是哪个词（`负面词` 和竞品词混在同一个清单里，处置方式完全不同）。判过但一条没中时写 `（未命中）`——空单元格要留给「这一轮压根没查过」 |
| `流量状态` | **多选**（七个选项见下） | 人机共用。`爆帖预备` 等人工值机器不碰。⚠️ 必须建成多选 |
| `巡查状态` | **单选 或 文本** | 单选时先建好五个选项：`正常`、`疑似受限`、`已失效`、`刷新失败`、`跳过`（`冷却跳过`/`留待下一轮` 只出现在运行日志里，不写进表） |
| `诊断信息` | **文本** | 人话解释 + 上游原始错误。看不懂也能截图给 IT（带 request_id） |
| `最近检查时间` | **日期** | **必备列**：没建这一列 sweep 会直接拒跑——分层刷新没有依据，每一轮都会全表重刷烧钱。⚠️ **必须是普通「日期」字段**——建成系统的「最后更新时间」类型机器写不进去，而且任何人工编辑都会刷新它，分层刷新的节奏会被打乱。建议在字段设置里打开「显示时间」，方便肉眼核对巡查节奏。写的是**这一行处理完的那一刻**（不是整轮开跑那一刻），和运行日志里那一行行首的时间逐字相同——见「拿日志对表」 |
| `已确认存活` | **复选框** | 本轮**真的量到至少一个数字**（评论数不是 None，哪怕是 0；抖音还看赞藏）→ 勾上；连续两次确认失效 → 取消。评论页空壳且 detail 兜底也失败、这轮对存亡零信息的轮次不动 |
| `连续失败次数` | **数字** | 两击定罪的计数器（只计「取不到内容」，网络失败不计）。建议隐藏 |

### `评论状态`（单选，由关键词命中驱动，直接覆盖）

先建好这两个选项：

| 值 | 什么时候写 |
|---|---|
| `显示评论` | 任一评论关键词出现在第一页任一条评论里 |
| `没有显示` | 配了关键词，但第一页一条都没命中 |

机器**直接覆盖**当前值——单选只显示当前状态，`待评论` 这类人工排期
旧值会被结论覆盖（选项可以留着给人工用，机器不需要它）。
两个平台都能判——匹配的是第一页评论内容，不依赖置顶字段，抖音行同样有效。
没填关键词的行、以及本轮没看到评论页内容的空壳轮不下结论、不碰这一列。

### `负面状态`（单选，由 `负面词` 命中驱动，直接覆盖）

先建好这两个选项：

| 值 | 什么时候写 |
|---|---|
| `有负面` | 任一负面词/竞品词出现在第一页**别人**的评论里 |
| `无负面` | 配了负面词，但第一页一条都没命中 |

**自家账号的回复不算。** 这一列问的是「别人在底下说了什么」，
品牌号自己回的「温和配方，不会过敏」按字面照样命中，会把一条干净的
帖子写成「有负面」。`评论关键词` 那边**不跳过**作者——自家置顶的引导
评论正是它要找的东西，两个方向天生相反。（作者标记只有小红书的评论
条目带，抖音一律没有，所以抖音行上这个排除等于没开。）

和 `评论状态` 是同一套机制、相反的方向，判定闸门也完全一样：
没填 `负面词` 的行不碰、本轮没看到评论页内容的空壳轮不碰。
后者尤其重要——**拿上游缺数当「无负面」写进表里，等于给运营一个假的安全感**，
那比不判还糟。这里的「看到过」有严格定义：**拿到了评论条目，或者确认了
评论数就是 0**。只知道「这条帖子有 150 条评论」但一条都没取到，不算看到过
——那种轮次三个结论（负面状态、评论状态、评论区快照）全都保持原样。
两个平台都能判（匹配的是评论正文，不依赖置顶字段）。

> ⚠️ **这一列是预警，不是普查。** 它只看第一页评论（和 `评论区快照` 同一份），
> 埋在第二页往后的负面评论看不见。这是刻意的取舍：翻页要按页计费，
> 一条帖子翻十页就是十倍成本。要做完整的口碑普查，那是另一件事、另一笔预算。

### `置顶状态`（单选，机器直接覆盖）

先建好这三个选项：

| 值 | 什么时候写 |
|---|---|
| `置顶成功` | 本轮第一页有置顶评论（自家帖子，有置顶即我方置顶在） |
| `置顶掉了` | **此前是 成功/掉了**，本轮没置顶了 |
| `无置顶` | 从来没成功过，现在也没有 |

「掉了」和「从来没有」的区分全看这一列自己的历史；掉了之后一直没恢复
保持「置顶掉了」，不退回「无置顶」。从「置顶成功」掉下来的那一轮，
`诊断信息` 里会额外报「置顶已不在」。
只有小红书能判（抖音评论接口没有置顶字段），**抖音行完全不碰这一列**；
空壳轮（评论和评论数都没拿到）也不碰、不误报。

### `流量状态`（多选）

机器只碰这七个词，**必须先建好选项**：

| 标签 | 什么时候打 |
|---|---|
| `观察中` | 发布不满 48 小时、评论数还不足 20——**还没到下结论的时候**，不是没起来 |
| `无水花` | 发布 48 小时后评论数仍不足 20——没起来，不是异常 |
| `评估中` | 评论数 ≥ 20 |
| `爆贴` | 评论数 ≥ 50 |
| `大爆` | 评论数 ≥ 100 |
| `风控中` | **只认硬证据**：上游返回了审核/受限标记，或链接失效（连续两次取不到；上游权威确认「已删除」第一次就判） |
| `疑似限流` | 评论数从有量的基线**突然腰斩**（跌幅超 50%，基线 ≥ 20）——数字异常，也可能是删评/折叠 |

> **`观察中` 是 2026-08 补的，专门治「新发的一批帖子 `流量状态` 全是空的」。**
> 在它之前，冷启动窗口（48 小时）内评论数没过 20 的行**一个标签都不打**，
> 那一格就是空的——而空格在运营眼里有三种读法：还没轮到它、轮到了没结论、
> 机器坏了。分不出来就只能一条条手工去填。现在这三种情况分别是
> `观察中`、有档位、`巡查状态` 非「正常」，一眼就分得开。
> 到 48 小时它会自动升成 `无水花` 或更高档，**不需要任何人去清**。
> 建完选项之前机器写不进去（会被安全跳过并在 `诊断信息` 里说明，不会写坏表），
> `doctor` 会点名提醒。不想要这一档就设 `TAG_OBSERVING=`（留空）关掉，
> 已经写出去的 `观察中` 下一轮会被自动摘掉。

**热度档位（观察中→无水花→评估中→爆贴→大爆）互斥且只升不降**；
`风控中`/`疑似限流` 每轮重算，恢复自动摘掉。
判定**只基于评论数**。（曾经还有点赞/收藏两组参考列，从来不参与打标签，现已整组去掉——见文末「已去掉的列」。）
`爆帖预备` 以及未来新增的任何选项机器零权限。
旧版本打过的 `已失效` 标签已并入 `风控中`，残留旧值下一轮会被自动摘掉，
表里的这个选项可以留着（历史筛选用）也可以删掉。

## 二·五、拿日志对表（为什么以前对不上）

出过一次「日志和表里的记录对不上，尤其是巡查时间」。三个原因叠在一起，
现在三个都堵住了：

| 以前 | 现在 |
|---|---|
| 容器日志行首的时间戳是 **UTC**，表里那一格是飞书按租户时区渲染的**北京时间**——差 8 小时 | 每一行日志自己带上按 `DISPLAY_UTC_OFFSET`（默认 +8）渲染的时刻，和表里那一格**逐字相同**；开跑那行两个时区都打，换算摆在眼前 |
| `最近检查时间` 盖的是**整轮开跑**那一刻，几百行共用一个值，比日志里那一行早好几分钟 | 每一行盖**自己处理完**的那一刻 |
| 逐行日志按提交顺序产出，前一行卡住时后几行会**攒在一起**冲出来，日志自己的时间戳更靠后 | 行首打印的是这一行落表的那个值，不是打印动作发生的时刻 |
| stdout 默认**块缓冲**，几十行攒够 8KB 一起吐出去，云平台给整块打同一个时间戳、块内顺序还会乱（表头跑到结论后面、「已写回 N 行」打完了还在出逐行结果） | 逐行 flush，每一行都带自己真实的时刻和真实的先后顺序 |

对表的方法：

```
⏱ sweep 开跑：2026-08-26 08:07:14 +08（UTC 00:07:14，容器日志用的就是这个）
━━━━ 表：西屋第一期 ━━━━
待刷 12 行，预计花费 ≈ ¥0.86
  [08:07:21] recvs93vQ1qhHs → 正常 发布 32 小时评论数 4，还在 48 小时冷启动窗口内，暂不下结论 → 观察中
  ...
已写回 12 行，本轮「最近检查时间」= 2026-08-26 08:07:21 +08 ~ 08:07:46
```

行首的 `[08:07:21]` 就是这一行 `最近检查时间` 那一格的值——直接搜就能对上。
`[  --  ]` 表示这一行本轮**没有**推进时间戳（冷却跳过、留待下一轮、熔断作废）。

还有一种「对不上」不是 bug：**分层巡检（sweep）和排队刷新（queue）通常是两个独立的
定时任务，各有各的日志**。在 queue 的日志里翻不到某一行的巡查记录，
它多半是被 sweep 那个任务刷的，反之亦然。开跑那行会打出模式，先看清是哪一个。

## 四、应用权限设置（最容易卡住的一步）

1. 飞书开放平台建**企业自建应用**，开权限 `bitable:app`，**发布版本并等审批通过**。
2. 打开目标多维表格 → 右上角 `…` → `更多` → **`添加文档应用`** → 搜应用名 → 添加，权限「可编辑」。
   表格挂在知识库（Wiki）里也是这一步，找法一样，不需要额外权限。
3. **如果这张表开了「高级权限」**：还要在高级权限里给应用 **「可管理」**。
   ⚠️ 漏这一步的表现是**读到空结果而不是报错**。
4. `python3 cli.py doctor` 全绿再开跑——它会按本文档逐列核对：
   列在不在、类型对不对、机器要写的选项建没建。
