## 零、先做一个决定

这套东西要一直有个"东西"在定时跑。三个候选，按你**已经有的资源**排：

| | **Railway** | GitHub Actions | 自建 VPS |
|---|---|---|---|
| 你已付费 | ✅ | 免费 | ❌ ¥24–60/月 |
| 跑这个服务的增量成本 | **约 $0.1/月**（实测） | ¥0 | 含在机器费里 |
| 勾选后多久有反应 | 5–10 分钟 | 10–70 分钟 | **1 分钟** |
| 跑的代码从哪来 | ✅ **直连 git 仓库** | ✅ git 仓库 | ✅ git 仓库 |
| 单次执行上限 | 无 | 6 小时 | 无 |
| 600 行全量刷一遍 | 一口气约 12–15 分钟 | 一口气约 12–15 分钟 | 一口气约 12–15 分钟 |
| 改完逻辑怎么上线 | `git push` 自动部署 | `git push` | `git pull` |
| 服务器位置 | 境外（美/欧/新加坡） | 境外 | 可选 |
| 出错了怎么查 | 面板日志 | 面板日志 | 日志文件 |

### 主方案：Railway

理由只有一条，但它比其他所有差异加起来都重要：**Railway 直接连 git 仓库部署。**
`git push` 就自动重新上线，跑的永远是仓库里那一版。这套东西每天往表里写几百次，
运营完全依赖它——"跑的到底是哪一版"这件事必须是确定的。
勾选响应 5–10 分钟（Railway 的 cron 最小间隔就是 5 分钟），够用。

### 扣子方案已退役

早期版本维护过一条「打包成单文件粘进扣子代码节点」的并行运行时
（境内、触发器 1 分钟、60 秒硬上限）。定下 Railway 之后它已从主干移除：
那条路跑的是一份**粘贴的副本**，没有任何办法验证线上和仓库一致，
而且每改一次逻辑都要重新生成、重新粘贴、双份维护判定口径——这份税
与「专注一个方案」直接冲突。

**完整实现保存在 [`coze-legacy`](https://github.com/TangVarie/linkcheck/tree/coze-legacy)
分支**（`tools/build_coze_node.py`、`coze_node.py`、`tests/test_coze_bundle.py`、
`docs/扣子工作流搭建说明.md` 都在），那是扣子 bundle 与主逻辑**完全同步的
最后一版**（= PR #2 合并时的 main）。将来要重启这条路：先把 main 合并进
`coze-legacy`、按新逻辑更新打包脚本的 FOOTER、重新生成 `coze_node.py`，
再照该分支里的 `docs/扣子工作流搭建说明.md` 部署。

## 一、通用前置（不管选哪个方案都要做）

### 1.1 数据通道账号（双通道，两家都建最好，只建一家也能跑）

**TikHub（主通道，便宜一半）**

去 <https://user.tikhub.io> 注册 → 验证邮箱 → 用户中心创建 API 令牌 → 充值。
支付支持银联卡（走 PayPal 的「信用卡/借记卡」，不用注册 PayPal）和 USDT。

- 充多少：600 条帖子分层刷新约 **$131/月 ≈ ¥946**。建议**先充 $20 试跑一周**。
- ⚠️ 大陆网络请求 `api.tikhub.dev`（代码里已写死），`api.tikhub.io` 被墙。
- ⚠️ 每日签到送的免费额度**用不到小红书接口**（`allow_free_credit=0`），
  想验小红书必须先充钱；抖音接口可以白嫖。

**SocialDataX（备胎，主通道倒下时顶上）**

去 <https://socialdatax.com> 注册 → 后台创建 API Key → 充值。

- 全平台 ¥0.10/次，比 TikHub 贵，但错误码是有契约的（`1006` 封控 / `1008` 已删除），
  判失效更准。平时不花钱，只在降级时才用到，所以**充一点点就够**——建议 ¥50。

⚠️ 两个 Key 都只显示一次，存好。它们就是钱，泄露了别人能直接花。

**只想先用一家**：另一个环境变量留空即可，代码会自动把没配 Key 的通道滤掉。
但那样就没有降级能力——半夜 Key 失效或余额见底，就是一整晚的监控全丢。

### 1.2 飞书自建应用

1. 打开 <https://open.feishu.cn/app> → **创建企业自建应用**
2. 左侧「权限管理」→ 搜索并开通 **`bitable:app`**
3. 左侧「版本管理与发布」→ **创建版本 → 申请发布**（要等管理员审批通过）
4. 「凭证与基础信息」页记下 **App ID** 和 **App Secret**

> **想让面板「直接新建一张表」并自动加协作者**，再多开两个权限（同样要
> 重新发布版本）：`contact:user.id:readonly`（拿手机号换 open_id，
> 给管理员开权限要用）和 `im:chat:readonly`（列出应用所在的群，
> 给运营群开可编辑要用）。只跑 cron、不用这个功能的话不需要它们。
> 用法见 [`面板.md`](面板.md) 二·五。

### 1.3 把应用加进那张多维表格（最容易卡住的一步）

> **面板新建的表跳过这一步**：那张 base 是应用自己建的，应用天生就是所有者。
> 这一节说的是**接管一张已有的业务表**。

打开目标多维表格 → 右上角 `…` → `更多` → **`添加文档应用`** → 搜应用名 → 添加。

搜不到应用时按顺序查这三条：

- 操作人是不是文档所有者、或有管理权限
- 应用的**已发布版本**可用范围有没有包含文档所有者
- 应用有没有**至少开通一个云文档 API 权限**（没开通根本不会出现在搜索框里）

⚠️ **如果这张表开了「高级权限」**：光加协作者不够，还要进高级权限给这个应用 **「可管理」**。
漏这一步的表现是**读到空结果而不是报错**，最容易卡住半天。

### 1.4 记下表格的两个 ID

多维表格的地址长这样：

```
https://xxx.feishu.cn/base/bascnABCDEFG1234567?table=tblXYZ7890&view=vew...
                            └────────┬───────┘        └───┬────┘
                             FEISHU_APP_TOKEN      FEISHU_TABLE_ID
```

> 表格如果挂在知识库（Wiki）里，地址栏会是 `/wiki/wikcnXXX?table=tblXYZ789`
> 这种形式——`FEISHU_TABLES`（见下方多表配置）直接认这种链接，地址栏那段
> token 直接当 app_token 用，接口照样认，不用手动去找 `/base/` 版本、
> 也不用额外开权限。单表模式的 `FEISHU_APP_TOKEN` + `FEISHU_TABLE_ID`
> 这两个变量不支持整条链接，只认裸的 token 字符串（把 `/base/` 或
> `/wiki/` 后面那段、以及 `table=` 后面那段分别抠出来填）。

### 1.5 建列、建选项

照 [`docs/表结构.md`](表结构.md) 建好列——那是**全量设置说明**，每列的
字段类型、选项和内在配置都在里面。**选择列的选项必须先手工建好**，
机器不会自动创建：

- `流量状态`（多选）：无水花 / 评估中 / 爆贴 / 大爆 / 风控中 / 疑似限流
- `评论状态`（单选）：显示评论 / 没有显示（由「评论关键词」命中结果驱动）
- `置顶状态`（单选）：置顶成功 / 置顶掉了 / 无置顶

> **这一节多数时候不用手工做。** 面板起来之后：接管已有表就点「体检一下」
> → 「补齐缺的列」（纯追加，已有的列一个都不碰）；从零开一个项目就点
> 「直接新建一张」，近 40 列连类型带选项一次建齐。手工建列的价值只剩一个：
> 面板还没部署起来的时候。

## 二、先在本地跑通（5 分钟，强烈建议）

不管最终放哪，**先在自己电脑上跑一次 `doctor`**。它不花一分钱，
但能一次性验证权限、字段名、选项是否齐全——九成的"配好了跑不通"都卡在这里。

需要电脑上有 Python 3.11 或更高版本（`python3 --version` 查）。

```bash
git clone https://github.com/TangVarie/linkcheck.git
cd linkcheck

cp .env.example .env
# 用编辑器把 .env 里五个值填上

set -a && source .env && set +a
python3 cli.py doctor
```

全绿了再往下走。没绿就照它给的提示改——每条提示都写了具体怎么办。

然后可以试跑一行不花几毛钱：

```bash
python3 cli.py estimate          # 只算钱，不发请求
python3 cli.py row recXXXXXXXX   # 刷一行（record_id 在飞书里右键记录 → 复制记录链接，末尾那段）
```

> 那一份是给真要动手的人看的，这一份只是四个方案的横向对比。

1. <https://railway.com> → `New Project` → **`Deploy from GitHub repo`** → 选 `linkcheck`
2. 它会自动构建。项目里那个空的 `requirements.txt` 就是给它认「这是 Python 项目」用的，

| `SOCIALDATAX_API_KEY` | SocialDataX 后台复制的 Key（备胎；只用一家的话可以不填） |
| `FEISHU_APP_ID` | 飞书应用的 App ID |
| `FEISHU_APP_SECRET` | 飞书应用的 App Secret |
| `FEISHU_APP_TOKEN` | 表格地址里 `/base/` 后面那段 |
| `FEISHU_TABLE_ID` | 表格地址里 `table=` 后面那段 |

### A3. 先跑体检

Service → `Settings` → `Deploy` → **Start Command** 填：

```

```

重新部署，看 `Deployments` → 日志。全绿了再往下。

这一步同时验证配置对不对、以及 Railway 的机器能不能连上飞书。不花一分钱。
`doctor` 会逐平台打印通道状态：主通道是谁、有没有备胎、Key 配没配。

### A4. 配成**一个**定时服务

> ⚠️ **这一节在 2026-08 的审计后改过，改法和结论都很重要，别照旧文档配。**
>
> 旧版让你建两个 Railway 服务（一个跑 `queue`、一个跑 `sweep`），依据是
> 「Railway 上一轮没跑完，下一轮直接跳过」。那句话是对的，但它的作用范围是
> **同一个 cron service**——它拦不住 queue 和 sweep 这两个**不同的服务**
> 同时开跑。而且两边的调度在 UTC `00:05 / 08:05 / 16:05` 还会天然撞在同一分钟。
>
> 两个进程同时刷同一张表的后果是三件事一起中招：同一批行被调两遍（钱花两份）、
> 两份基于各自旧快照的整列写入互相覆盖（人工标签丢更新）、同表并发写
> （飞书返回写冲突 1254291）。
>
> 仓库里的运行租约（`xhsearch/runlock.py`）是文件锁，**跨容器不生效**，
> 救不了这个拓扑。所以规矩是：**定时调度只能有一个地方跑。**

Railway 的 cron 是一个服务一个调度，所以把两种模式合进**同一个服务**、
按顺序串行执行：

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py queue && python3 cli.py sweep` |
| Cron Schedule | `*/5 * * * *` |
| Restart Policy | **`Never`** |

`sweep` 本身有分层节流：没有到期的行时它读一次表就退出，不发任何付费请求，
所以每 5 分钟带着跑一次并不会多花钱，只是把「到期检查」的粒度变细了。
想更省一点，也可以只跑 `queue`，另外**在同一个服务里**用一个包装脚本按
小时判断要不要接着跑 `sweep`——关键是「只有一个 cron service」，
而不是「只有一条命令」。

⚠️ 用 `&&` 串联时，`queue` 返回非零（真故障）会让 `sweep` 不执行。想让两者
互不影响就写成 `python3 cli.py queue; python3 cli.py sweep`；想让任一失败都
体现在退出码上，就保留 `&&`。两种都对，取决于你希望 Railway 的运行记录
反映什么。

如果你**确实**需要拆成两个服务（比如两张表分给两台机器跑，各刷各的），
那就必须保证它们**读写的表没有交集**，并且给每个服务配不同的 `FEISHU_TABLES`。

### A5. 四个必须知道的 Railway 行为

**① Restart Policy 一定要设成 `Never`。** 这是最能烧钱的一个坑。

定时任务跑完就退出，而默认的重启策略是 `On Failure`。如果哪天 Key 过期、
积分耗尽，程序退出码非零，Railway 会**反复重启它**——变成一个高频循环。
设成 `Never` 就没这回事。

（代码这边也配合做了：只有真故障才返回非零。到软截止把剩余的行留给下一轮
属于正常运行，返回 0。）

**② cron 最小间隔是 5 分钟。** 想要 1 分钟响应只能上自建 VPS。
而且启动时间会漂移几分钟，所以勾选后的实际体感是 **5–10 分钟**。

**③ 上一轮没跑完，下一轮直接跳过。** 这是**按 cron service** 生效的：
它保证同一个服务不会有两个实例并行，**但保证不了两个不同的服务**——
这就是上面 A4 要求合成一个服务的原因。

单轮规模也别只靠"应该跑得很快"：设 `MAX_RECORDS_PER_RUN`（比如 40）
给它一个硬上界。超出的行保持原样（排队勾还在、检查时间没动），
下一轮自然继续，不会丢。

**④ cron 走 UTC。** 北京时间减 8 小时。

### A6. 要花多少钱

Railway 按「资源 × 分钟」计费，而**内存通常是账单里最大的一项**。

实测这个服务的峰值内存：**28 MB**（600 行时；解释器加全部导入的基线是 24.5 MB）。
纯计算耗时 0.18 秒——绝大部分时间是在等网络，不吃 CPU。

按 Hobby 套餐的单价估算每月增量：

| 项目 | 用量 | 费用 |
|---|---:|---:|
| Memory | 约 6–12 万 MB·min | $0.01–0.03 |
| vCPU | 约 2,000–4,000 vCPU·min | $0.01–0.02 |
| Network | 约 0.7 GB | $0.04 |
| Disk | 不写盘 | $0 |
| **合计** | | **约 $0.1/月** |

估算基于：每 5 分钟起一次容器（288 次/天），每次冷启动 + 干活按 30 秒算。
大部分轮次读一次表发现没有到期的行就直接退出，几秒钟的事。

> **cron 比常驻便宜十倍。** 常驻进程是 24×30 天 = 43,200 分钟 × 28 MB
> ≈ 121 万 MB·min ≈ $0.28/月；cron 只在跑的时候计费。
> 所以别把它改成「起一个进程自己 sleep 循环」，那样反而贵。

真正的成本大头是**数据接口**（走 TikHub 约 ¥950/月，全走 SocialDataX 约 ¥1,900/月），
不是 Railway。

### A7. 以后怎么改

改 `xhsearch/` 下的代码 → `git push` → **Railway 自动重新部署**。
不用登面板，不用粘贴任何东西，跑的永远是仓库里那一版。

要改刷新频率就改面板里的 Cron Schedule；要改判定口径（阈值、分层间隔）
改 `config.py` 然后 push。

## 方案 C：GitHub Actions（不额外花钱，但响应最慢）

不额外花钱。适合「暂时不想动现有会员、先跑起来看看」。\n\n⚠️ **`refresh.yml` 里的定时任务默认是注释掉的**，因为一套定时只能有一个地方跑——Railway 和这里同时开，会重复刷同一张表、重复花积分。选了这个方案才去把注释解开。

### C0. ⚠️ 先把 PR 合了

**GitHub 的定时任务只在默认分支上生效，`workflow_dispatch` 手动触发也要求
工作流文件已经在默认分支上。**

也就是说：这个 PR 合并之前，`Actions` 页面里根本看不到「刷新监控表」，
定时任务一次都不会跑，手动也点不了。这不是配错了，是 GitHub 的规则。

顺序必须是：**先合 PR → 再填 Secrets → 再跑 doctor**。

（合并之后如果还想在功能分支上试，可以在 `Run workflow` 的下拉里选分支——
但前提仍然是工作流文件已经在默认分支上存在过。）

### C1. 填 Secrets

打开仓库 → `Settings` → `Secrets and variables` → `Actions` → `New repository secret`，
建这几个：

| 名字 | 值 |
|---|---|
| `TIKHUB_API_KEY` | TikHub 用户中心复制的令牌（主通道） |
| `SOCIALDATAX_API_KEY` | SocialDataX 后台复制的 Key（备胎；只用一家的话可以不填） |
| `FEISHU_APP_ID` | 飞书应用的 App ID |
| `FEISHU_APP_SECRET` | 飞书应用的 App Secret |
| `FEISHU_APP_TOKEN` | 表格地址里 `/base/` 后面那段 |
| `FEISHU_TABLE_ID` | 表格地址里 `table=` 后面那段 |

Secrets 存在 GitHub 这边，**不会出现在代码里**，也不会打印到日志里。

### C2. 先跑体检

仓库 → `Actions` 标签 → 左侧选「刷新监控表」→ 右上 `Run workflow` →
模式选 **`doctor`** → 跑。

这一步同时验证两件事：配置对不对，以及 **GitHub 的机器能不能连上飞书**（服务器在境外）。
`doctor` 会逐平台打印通道状态。

`doctor` 不发业务请求，所以验不了「数据通道通不通」。那个用：

```bash
python3 tools/probe_channel.py <一条真实笔记链接>
```

会真发请求、真扣费（约 ¥0.15），但它走的就是线上那一份代码，验的是真东西。

绿了再依次试 `estimate` → `queue` → `sweep`。

### C3. 定时任务已经配好了

`.github/workflows/refresh.yml` 里定了两条：

- **每小时**跑一次 `queue`——处理勾了「排队刷新」的行
- **每天 08:05 / 16:05 / 00:05（北京时间）**跑 `sweep`——分层巡检

改频率就改那个文件里的 `cron`。**改完必须合进默认分支才生效**（见 §C0），而且要先把 `schedule` 那几行的注释解开。

两个会让它悄悄停掉的坑：

- **定时任务默认是关的**，第一次要在 `Actions` 页面手动 `Enable workflow`
- **仓库连续 60 天没有任何提交**，GitHub 会自动停掉定时任务并发邮件通知。
  失败模式是静默的——表就是不更新了，没人会注意到。建议在日历上放一个季度提醒，
  或者干脆每季度推一个空提交

### C4. 关于免费额度

私有仓库每月 **2000 分钟**免费。按上面的配置估算：

```
每小时 queue：24 次/天 × 1 分钟（不足 1 分钟按 1 分钟算）= 720 分钟/月
每天 3 次 sweep：3 × 约 5 分钟 = 450 分钟/月
────────────────────────────────────────────
合计约 1170 分钟/月，在 2000 以内
```

**如果想把 queue 提到每 15 分钟**，就是 96 次/天 = 2880 分钟/月，**会超**。
那时候要么把仓库改成公开（公开仓库 Actions 不限量），要么就该搬去服务器了。

### C5. 这个方案的真实短板

**定时任务不准点。** GitHub 的 cron 高峰期会延迟十几分钟，偶尔整个跳过一次。
所以"勾了「排队刷新」之后多久有反应"实际是 **10–70 分钟**，不是"一小时整"。

对定时巡检完全没影响（8 小时一档，晚十几分钟无所谓）。
但如果运营的心理预期是"勾完去倒杯水回来就好了"，那这个方案会让人失望。

## 方案 D：自建 VPS（唯一能做到 1 分钟响应的）

### D1. 买机器

腾讯云轻量应用服务器 / 阿里云轻量，**2核2G，Ubuntu 22.04**，约 ¥24–60/月。

**地域选香港或新加坡**，两个原因：不用备案（国内地域绑域名要备案，虽然这个方案
根本不需要域名，但省得以后麻烦），而且 SocialDataX 的服务器本身就在腾讯云香港，同城延迟低。

这个方案**不需要域名、不需要备案、不需要开任何入站端口**——它只往外发请求，
不接受任何外部访问。只留 SSH。

### D2. 装环境

SSH 上去，一路复制粘贴：

```bash
sudo apt update && sudo apt install -y python3 git
git clone https://github.com/TangVarie/linkcheck.git
cd linkcheck

cp .env.example .env
nano .env                    # 填五个值，Ctrl+O 保存，Ctrl+X 退出
chmod 600 .env               # 只有自己能读，.env 里是钱和密钥

set -a && source .env && set +a
python3 cli.py doctor        # 全绿再往下
```

### D3. 挂定时任务

```bash
crontab -e
```

粘进去（注意把 `/root/linkcheck` 换成你实际的路径，`pwd` 可以查）：

```cron
# 每分钟处理勾了「排队刷新」的行 —— 运营勾完最多等 1 分钟
* * * * * cd /root/linkcheck && flock -n /var/lock/xhsearch.lock -c 'set -a && . ./.env && set +a && /usr/bin/python3 cli.py queue' >> /var/log/xhsearch.log 2>&1

# 每天 08:05 / 16:05 / 00:05 分层巡检
5 0,8,16 * * * cd /root/linkcheck && flock -n /var/lock/xhsearch.lock -c 'set -a && . ./.env && set +a && /usr/bin/python3 cli.py sweep' >> /var/log/xhsearch.log 2>&1
```

⚠️ **两条都要用 `flock`，而且必须是同一个锁文件。** 这两条 cron 在
`00:05 / 08:05 / 16:05` 会撞在同一分钟；只给 `queue` 加锁等于没加。
`flock -n` 的意思是「拿不到锁就直接退出」，不排队不等待。

（代码里的运行租约会做同样的事，`flock` 是第二道保险，也让"被跳过"这件事
在系统日志层面就看得见。两者用的是不同的锁文件，互不干扰。）

⚠️ **cron 的环境变量和你 SSH 登录时不是一套**，所以每条命令都要自己 `. ./.env`。
这是 cron 任务"手动跑好好的、定时跑就不动"最常见的原因。

看日志：

```bash
tail -f /var/log/xhsearch.log
```

### D4. 别让日志把磁盘撑满

```bash
sudo tee /etc/logrotate.d/xhsearch > /dev/null <<'EOF'
/var/log/xhsearch.log {
    weekly
    rotate 4
    compress
    missingok
    notifempty
}
EOF
```

### D5. 每分钟跑一次会不会打架

`queue` 模式只捞勾了「排队刷新」的行，没勾的时候它读一次表就退出，
几乎不耗资源，**也不花积分**（没有行就不发业务请求）。所以频率本身不是问题。

会打架的是**重叠**：上一轮还没跑完下一轮就起来了，或者 `queue` 和 `sweep`
在同一分钟撞上。上面 D3 里两条 cron 都已经包了同一个 `flock`，那是必须的，
不是"行数多的时候值得加"。

代码这边还有第二道：所有付费入口（`queue` / `sweep` / `row`）在开跑前会先拿
一个运行租约（`xhsearch/runlock.py`），拿不到就干净退出、一个请求都不发。

```bash
# 想换锁文件位置（比如 /tmp 是 tmpfs、重启会清空）：
RUN_LOCK_PATH=/var/lib/xhsearch/run.lock
```

⚠️ 两道锁都是**文件锁**，只在同一台机器/同一个文件系统上生效。一台 VPS 和一个
GitHub Actions runner 之间没有共享盘，两边同时跑就是两个付费执行者——
所以「定时调度只能有一个地方跑」是部署纪律，不是代码能兜住的事。

## 三、上线第一周该盯什么

1. **每天看一眼余额**。刷新报告最后一行会打印本轮花费、各通道各用了几次、
   以及有没有发生降级。**降级次数持续不为 0 就说明主通道有问题**，
   那时候还在正常出数只是因为备胎在扛——别等备胎也倒了才发现。
   烧得比预期快，就调 `config.py` 里的 `RefreshTiers`（把老帖的间隔拉长最省钱）。
2. **收集「诊断信息」里的怪话术**。笔记被删/被封控实际会命中哪个错误码
   （1003 / 1006 / 1008），只有真数据能告诉你，见 [`docs/待验证清单.md`](待验证清单.md)。
3. **看爆贴阈值准不准**。20 / 50 / 100 是拍的，跑一周拿真实分布回来调。
   改 `config.py` 里的 `Thresholds` 就行，不用动别的。

## 四、排错

| 症状 | 多半是什么 |
|---|---|
| `doctor` 卡在第 ① 步 | app_id / app_secret 填错，或应用还没发布通过审批 |
| `doctor` 说读不到字段列表 | 没做 §1.3「添加文档应用」，或高级权限没给「可管理」 |
| 读到 0 行但表里明明有数据 | 高级权限没给应用「可管理」（表现是空结果不是报错），或者没有行勾了「是否巡查」 |
| `1254045 FieldNameNotFound` | 列名和 `config.py` 对不上，差一个空格也不行 |
| `1254060` 字段类型不对 | 数字列被写了字符串，或日期列没给毫秒时间戳 |
| `1254063 MultiSelectFieldConvFail` | 某一列的**类型**建错了：最常见是「流量状态」建成单选（机器按多选写列表），或「评论状态」「负面状态」「置顶状态」建成多选（机器写字符串）。跑 `doctor --table 表名` 会指出是哪一列。程序现在会把这一列单独摘掉、其余列照写，日志里那段 `❌ 这些列的字段类型…` 就是它（那一轮退出码非零，别忽略） |
| 日志说「调度地基列的类型不对，本轮不跑」 | `最近检查时间` 或 `排队刷新` 建错了类型。这两列写不进去会让每一轮重新付费刷同一批行，所以自动模式在花钱之前就拒跑。按提示改类型即可，**没有花钱** |
| 某些标签一直不出现 | 那个选项在多选字段里还没建。`doctor` 会列出缺哪些 |
| 手动跑好好的、定时跑不动 | cron 没有加载 `.env`，见 §B3 |
| 表里一片「疑似受限」 | 先别慌。看诊断信息里的 request_id 和错误码；如果是整批出现，熔断已经拦住了标签写入 |
| 抖音行的「置顶评论」永远是那句话 | 这是对的。抖音接口没有 `is_pinned`，判不了 |
| **新表勾了一批「排队刷新」，刷了 20 行就停了** | `FIRST_RUN_MAX_RECORDS`（默认 **20**）。整张表**一个**「最近检查时间」都没有时，一轮只刷前 20 行——防的是「800 行的新表刚入册就吃掉整轮预算」。剩下的勾还在，下一轮 cron 再来 20 行，几轮之后铺满。日志里有一行 `🐣 这张表一个「最近检查时间」都没有…本轮只刷前 20 行`。想一次刷完：`FIRST_RUN_MAX_RECORDS=0`（**注意这会让新表首轮按你勾的行数一次性花钱**） |
| 勾了「排队刷新」但那一行没动，也没报错 | 三种可能：① 90 秒**同行冷却**——刚刷过的行再勾会被跳过（不计费），日志里是 `冷却跳过`；② 本轮撞上 `MAX_RECORDS_PER_RUN` / `MAX_YUAN_PER_RUN`，剩余行留给下一轮；③ 那张表在注册表里被**停用**了——停用的是整张表，cron 根本不读它（面板会拒绝勾并说明）。行级的 `是否巡查` 不影响：勾排队照刷 |

### 「排队刷新」到底受哪些限制

按遇到的先后顺序：

| 闸 | 默认 | 什么时候咬人 |
|---|---|---|
| 面板单次勾选上限 | 200 行 | 只在面板上勾时。飞书里手工拖拽勾不受它管 |
| cron 频率 | 5 分钟 | 勾完到有反应的等待时间。想更快见上面「方案 D：自建 VPS」 |
| **首轮小闸** `FIRST_RUN_MAX_RECORDS` | **20 行** | **整张表一个「最近检查时间」都没有**时（= 全新表）。这是新表最常撞到的一个 |
| 同行冷却 `cooldown_seconds` | 90 秒 | 同一行 90 秒内刷过第二次。`cli.py row` 手工点名不受它管 |
| 单轮行数 `MAX_RECORDS_PER_RUN` | 建议 300 | 整次运行共享，多张表一起算 |
| 单轮金额 `MAX_YUAN_PER_RUN` | 建议 50 | 同上，且是唯一的**硬**上界 |
| 全局熔断 | 见 `config.py` | 一批里大面积取不到内容时整轮作废，不写标签 |

被闸拦下的行**不会丢**：勾还留在表里，也不推进「最近检查时间」，下一轮自然接着来。
