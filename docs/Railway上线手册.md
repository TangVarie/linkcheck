# Railway 上线手册

从零到跑起来，一步一步。**预计 60–90 分钟**，其中一半时间在等飞书管理员审批。

不需要写代码，不需要懂 Python。每一步都写了「做完应该看到什么」，
对不上就停下来看那一步末尾的「卡住了怎么办」。

---

## 为什么是 Railway（唯一主方案）

三条理由，第一条比其余所有差异加起来都重要：

1. **直接连 git 仓库部署**：`git push` 就自动重新上线，跑的永远是仓库里那一版。
   这套东西每天往表里写几百次、运营完全依赖它，「跑的是哪一版」必须是确定的。
2. **双通道已实测两条都通**：Railway 上用的是标准库，TikHub 要求的浏览器
   `User-Agent` 想怎么设怎么设（不带直接 403，实测踩过）。
3. **能跑 `doctor` 体检**、单次执行无时限，600 行一口气 12–15 分钟刷完。

勾选后要等 5–10 分钟（Railway 的 cron 最小间隔就是 5 分钟）。
对「看评论区氛围、判爆文、发现风控」这些事，这点差别不影响任何决策。

（早期并行维护的扣子代码节点路径已从仓库移除——粘贴副本没法验证与仓库
一致、双份维护判定口径，与专注一个方案冲突。详见 `docs/部署.md` 零节。）

## 三、飞书那边

**这一节最容易卡住，而且卡住的表现是「读到空结果而不是报错」**，所以每步都要确认。

### 3.1 建自建应用

1. <https://open.feishu.cn/app> → **创建企业自建应用**，名字随便起
2. 左侧「凭证与基础信息」→ 记下 **App ID** 和 **App Secret**
3. 左侧「权限管理」→ 搜 `bitable` → 开通 **`bitable:app`**（多维表格读写）
4. 左侧「版本管理与发布」→ **创建版本 → 申请发布**

**做完应该看到**：版本状态变成「已发布」。

> **卡住了怎么办**：状态卡在「审核中」= 要等管理员批。这一步没法绕过，
> 提前跟管理员打招呼能省半天。

### 3.2 ⚠️ 把应用加进那张表（最容易漏的一步）

**权限开了不等于能访问你那张表。** 还要在表里单独授权：

打开多维表格 → 右上角 `···` → **更多** → **添加文档应用** → 搜你刚建的应用名 → 添加 → **权限给「可编辑」**

**做完应该看到**：应用出现在协作者列表里，权限是「可编辑」。

> **漏了这一步的表现**：`doctor` 能取到 token、也能列字段，但**读记录读到 0 行**，
> 不报任何错。看到「读到 0 行」第一反应就该是回来检查这里。

### 3.3 建列和选项（全量设置说明在 表结构.md）

照 [`表结构.md`](表结构.md) 逐列建好——那份文档写清了**每一列的字段类型、
选项清单和内在配置**（哪列必须是多选、哪列不能用系统的「最后更新时间」类型、
哪列千万别建成超链接字段）。列名对了不等于配好了，类型和选项也要对。

最容易翻车的几处，先划重点：

- **选择列的选项必须手工先建好，机器不会自动创建**：
  - `流量状态`（**多选**）：`无水花` / `评估中` / `爆贴` / `大爆` / `风控中` / `疑似限流`
    ——人机共用标签列，机器按多选合并写入，人工值原样保留
  - `评论状态`（**单选**）：`显示评论` / `没有显示`
    ——由「评论关键词」命中驱动，机器直接覆盖当前值
  - `置顶状态`（**单选**）：`置顶成功` / `置顶掉了` / `无置顶`
    ——只记状态不记内容（置顶内容在快照第一行能看到）；抖音行不写
- ⚠️ 类型和写法必须配对：`流量状态` 建成单选、或两个状态列建成多选，
  写回都会失败。
- ⚠️ `最近检查时间` 必须是普通**日期**字段——建成系统的「最后更新时间」类型
  机器写不进去，而且任何人工编辑都会刷新它，分层刷新全乱。
- ⚠️ `反馈链接` 用**文本**字段，别用「超链接」——会规范化链接、可能吞掉
  小红书短链里的 token。
- `蓝词字段` 机器**不读不写**（蓝词是人工手机端自查的）；机器匹配用的是
  另一列 `评论关键词`，两者是两回事。命中的那条评论会出现在
  `评论区快照` 第一行、带「命中『词』」标记，不占单独一列。

⚠️ 列名要和 `xhsearch/config.py` 里的**逐字一致**，差一个空格飞书就报
`1254045 FieldNameNotFound`。你们表里叫别的名字就去改 `config.py`，那是唯一需要改的文件。

建完不用逐列人工核对：`python3 cli.py doctor` 会按 表结构.md 的口径做
**全量体检**（列在不在、类型对不对、选项建没建），第四步就跑它。

### 3.4 记下表格地址里的两段

表格地址长这样：

```
https://xxx.feishu.cn/base/bascnABC123DEF?table=tblXYZ789
                            └── app_token ─┘       └ table_id ┘
```

> 表格挂在知识库（Wiki）里的话，地址栏会是 `/wiki/wikcnXXX?table=tblXYZ789`
> 这种形式——不用另外去找"真正的" `/base/` 链接，`FEISHU_TABLES` 直接认
> `/wiki/` 链接：地址栏那段 token 直接当 app_token 用，多维表格接口照样认，
> 不用额外调接口换算，也不用多开权限，跟 `/base/` 链接一视同仁。

## 五、Railway

### 5.1 建项目

<https://railway.com> → `New Project` → **`Deploy from GitHub repo`** → 选你的新仓库

第一次用要授权 Railway 访问你的 GitHub。选仓库时如果列表里没有，
点 `Configure GitHub App` 把新仓库加进可访问范围。

**做完应该看到**：它自动开始构建，几十秒就完。
（仓库里那个空的 `requirements.txt` 就是给它认「这是 Python 项目」用的，别删。
这个项目零第三方依赖，没有东西要装。）

> **如果构建报 `No start command detected`**：这个项目是纯 CLI、没有
> `main.py`，Railway 的构建器（Railpack）猜不出启动命令。仓库里已带
> `railpack.json`（默认启动命令 = `python3 cli.py doctor`，不花钱），
> 拉到这个文件之后不会再报；报了就说明你的克隆还没有它——去服务的
> `Settings` → `Deploy` → **Custom Start Command** 手工填 `python3 cli.py doctor`
> 再 Deploy 一次即可。正式跑起来时本来就要改 Start Command，
> 界面上填的值**优先于** railpack.json 的默认值。

### 5.2 填环境变量（建在项目级）

项目页 → `Variables`（**项目级的，不是服务级的**：将来要加别的服务时不用再填一遍）

| 名字 | 值 |
|---|---|
| `TIKHUB_API_KEY` | TikHub 令牌 |
| `SOCIALDATAX_API_KEY` | SocialDataX Key |
| `TIKHUB_BASE` | **`https://api.tikhub.io`** ← 见下 |
| `FEISHU_APP_ID` | 飞书 App ID |
| `FEISHU_APP_SECRET` | 飞书 App Secret |
| `FEISHU_APP_TOKEN` | 表格地址里 `/base/` 后面那段（单表用） |
| `FEISHU_TABLE_ID` | 表格地址里 `table=` 后面那段（单表用） |

> **要巡查多张表**：不填上面两个，改填一个 `FEISHU_TABLES`——分号分隔，
> 每一项 `标签=app_token:table_id` 或 `标签=表格完整网址`，例如
> `FEISHU_TABLES=OKMAN一期=bascnXXX:tblAAA; OKMAN二期=https://xx.feishu.cn/base/bascnXXX?table=tblBBB`。
> 每个命令（doctor/sweep/queue/row）都会逐表执行，日志按标签分节，
> 一张表出故障不影响其余表。三个前提：①每张表都照 `表结构.md` 建列
> （列名/类型/选项一致）；②飞书应用要**逐张表**「添加文档应用」授权；
> ③新表先 `python3 cli.py doctor --table 标签` 单独体检一次。
> 加表就是改这一个变量，不用加服务、不用改代码。

> **`TIKHUB_BASE` 为什么要填**：TikHub 有两个同功能的域名，
> `api.tikhub.dev` 给境内、`api.tikhub.io` 是主域名，对方文档明确要求
> **「请勿跨区使用，会影响访问速度」**。Railway 的机器在境外，所以要切到 `.io`。
> 代码默认取 `.dev`（境内境外都通），不填也能跑，只是慢一点。

### 5.4 改成**一个**定时服务

> ⚠️ **2026-08 的审计推翻了这一节的旧写法，别照旧文档配。**
>
> 旧版让你建两个服务（一个 `queue`、一个 `sweep`），依据是「Railway 上一轮
> 没跑完，下一轮直接跳过」。那句话本身没错，但它的作用范围是**同一个
> cron service**——拦不住两个**不同的服务**同时开跑。而且两边的调度在
> UTC `00:05 / 08:05 / 16:05` 会天然撞在同一分钟。
>
> 两个进程同时刷同一张表 = 同一批行调两遍（钱花两份）+ 两份旧快照互相覆盖
> （人工标签丢更新）+ 同表并发写（飞书报 1254291 写冲突）。
>
> 代码里的运行租约是**文件锁**，两个 Railway 服务各有各的容器和文件系统，
> 它救不了这个拓扑。所以：**只建一个 cron service。**

就用刚才那个服务，改两处设置：

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py queue && python3 cli.py sweep` |
| Cron Schedule | `*/5 * * * *` |
| Restart Policy | **`Never`** ← 别忘 |

`sweep` 有分层节流：没有到期的行时它读一次表就退出，**不发任何付费请求**，
所以每 5 分钟带着跑一次不会多花钱，只是把「到期检查」的粒度变细了。

顺手把单轮上界也配上（`Variables` 里加）：

| 名字 | 值 | 作用 |
|---|---|---|
| **`MAX_YUAN_PER_RUN`** | 比如 `20` | **单轮金额硬上限。当成必配项。** |
| `MAX_RECORDS_PER_RUN` | `40` | 单轮最多处理 40 行，超出的行保持原样留给下一轮 |

🚨 **`MAX_YUAN_PER_RUN` 是三个闸门里唯一的硬上限**，也是下面这三类事故
唯一的共同兜底——它们的单轮成本都没有上界，而且**都不会报错**：

- 全表被误勾「排队刷新」
- 「最近检查时间」整列被清空 → 每一行都判到期 → 全表重刷
- 上游故障导致每轮熔断又每轮重刷（**TikHub 对失败的调用也计费**）

按你们一轮的正常花费给 3–5 倍。没设的话 `doctor` 的第 ⑤ 段和每一轮开跑
都会警告——但它只警告不拒跑，设不设是部署方的决定。

### 5.5 ⚠️ Restart Policy 一定要设成 `Never`

**这是这套部署里最能烧钱的一个坑。**

定时任务跑完就退出，而 Railway 默认的重启策略是 `On Failure`。
哪天 Key 过期、余额耗尽，程序退出码非零，Railway 会**反复重启它**——
变成一个高频循环，一晚上能烧掉不少钱，而且每一轮都在打上游接口。

设成 `Never` 就没这回事。

（代码这边也做了配合：只有真故障才返回非零。到软截止把剩余的行留给下一轮
属于正常运行，返回 0，不会触发重启。）

### 5.6 另外三个要知道的 Railway 行为

- **cron 最小间隔 5 分钟**，而且启动会漂移几分钟，所以勾选后的实际体感是 **5–10 分钟**。
- **上一轮没跑完，下一轮直接跳过。** Railway 不让两个实例并行——这正好帮我们避免了
  两个进程同时写一张表。`queue` 每轮只处理到期的行，几秒就完，撞不上。
- **cron 走 UTC**，北京时间减 8 小时。

### 5.6b 再加一个服务：监控面板（可选，强烈建议）

表多了以后，「哪个项目该管了」靠一张张点开飞书表是不现实的。面板把所有项目
拉到一屏，最上面是**跨表待办列表**——所有要处理的行拉平，点「去这一行」
直接落到飞书里那一行。完整说明见 [`面板.md`](面板.md)。

在**同一个 Railway 项目**里 `New Service` → 选同一个仓库：

| 设置项 | 值 |
|---|---|
| Start Command | `python3 cli.py serve` |
| Cron Schedule | **留空** |
| Restart Policy | `On Failure`（常驻服务，和 cron 那个相反） |
| Networking | `Generate Domain` |
| Health Check Path | `/healthz` |

项目级变量（飞书凭据、表清单）自动共享，只要再加两个：

| 名字 | 值 |
|---|---|
| `PANEL_PASSWORD` | 面板口令，**至少 12 个字符**。没设它面板会拒绝启动 |
| `FEISHU_DOMAIN` | `https://xxx.feishu.cn`，就是你打开多维表格时地址栏那一段 |

要在面板上加表删表，再跑一次 `python3 cli.py init-registry`（本地跑就行），
把它打印的 `FEISHU_REGISTRY=...` 加到**项目级**变量里——cron 和面板都要读它。
**这辈子只做一次**，之后加表全在面板上。

常驻进程约 $0.3–1/月。相对数据接口的 ¥950/月，这是噪声。

> ⚠️ **两条不能踩的线**
> 1. 面板服务**绝不能配 Cron Schedule**。
> 2. 面板服务的 Start Command 里**绝不能出现 `queue` 或 `sweep`**。
>
> 理由和 §5.4 是同一条：两个容器同时刷同一张表 = 钱花两份 + 人工标签被旧
> 快照覆盖 + 飞书 `1254291` 写冲突，而运行租约是文件锁，跨容器拦不住。
> **付费执行者永远只能有 cron 那一个。**
>
> 代码这边也上了闸：`xhsearch/panel.py` 不 import 供应商那一层、不调任何会发
> 付费请求的函数，有测试按 AST 逐个调用节点检查——面板从设计上就不许成为执行者。

### 5.7 要花多少钱

Railway 按「资源 × 分钟」计费，**内存通常是账单里最大的一项**。

实测这个服务的峰值内存 **28 MB**（600 行时；解释器加全部导入的基线是 24.5 MB），
纯计算耗时 0.18 秒——绝大部分时间在等网络，不吃 CPU。

| 项目 | 用量 | 费用 |
|---|---:|---:|
| Memory | 约 6–12 万 MB·min | $0.01–0.03 |
| vCPU | 约 2,000–4,000 vCPU·min | $0.01–0.02 |
| Network | 约 0.7 GB | $0.04 |
| **合计** | | **约 $0.1/月** |

> **别把它改成「起一个进程自己 sleep 循环」。** 常驻进程是 24×30 天 = 43,200 分钟
> × 28 MB ≈ 121 万 MB·min ≈ $0.28/月；cron 只在跑的时候计费，便宜十倍。

真正的成本大头是**数据接口**（约 ¥950/月），不是 Railway。

## 六、跑起来之后

### 6.1 每天看一眼

刷新报告最后一行长这样：

```
处理 40 行（正常 38，疑似受限 2），花费 ≈ ¥2.88（tikhub 68 次）
```

出现降级时会多一句：

```
花费 ≈ ¥3.10（socialdatax 12 次、tikhub 56 次），其中 12 次是主通道失败后降级完成的
```

> **降级次数持续不为 0 就说明主通道有问题。** 那时候还在正常出数，
> 只是因为备胎在扛——别等备胎也倒了才发现。去 TikHub 后台看余额和公告。

### 6.2 表里出现这些状态是什么意思

| 刷新状态 | 含义 | 要不要管 |
|---|---|---|
| `正常` | 取到数了 | 不用 |
| `疑似受限` | 第一次取不到内容，**只计数，一个标签都没打** | 观察，下一轮会复核 |
| `已失效` | 连续两次取不到 → 流量状态打 `风控中` | 人工确认一下是不是真被删了 |
| `刷新失败` | 网络/接口故障，**已有数据一个都没动** | 看「诊断信息」列 |
| `跳过` | 链接识别不了，或当前配置的通道不支持这种链接形态（如只配 TikHub 时的抖音短链） | 看诊断信息：补全链接或配上 SOCIALDATAX_API_KEY |
| `冷却跳过` | 90 秒内刚刷过，没花钱 | 不用 |
| `留待下一轮` | 到软截止/整批中止时没轮到，**表里什么都没写**，下一轮自动重捞 | 不用（只出现在日志里，不落表） |

诊断信息里如果出现 `⚠ 上游把这条标成了审核中/受限 → 风控中，请人工确认`——
那是上游自己的审核标记，是「风控中」认可的两种硬证据之一（另一种是链接失效），
机器会打上 `风控中`；这个字段还没在真被封的帖子上验过，所以仍请人工去平台
确认一下。评论数的异常不进风控：突然腰斩是 `疑似限流`，发布 48 小时还
起不来是 `无水花`。

### 6.3 熔断

一批里判失效的比例超过 20%（且样本 ≥ 10 行），**整批撤销标签写入**，
报告里会打 `🛑 已熔断`。

几百条笔记不可能在同一小时被集体删除，出现这个一定是上游挂了。
这一轮什么都不写是对的，不用管，下一轮自然恢复。

### 6.4 以后怎么改

改 `xhsearch/` 下的代码 → `git push` → **Railway 自动重新部署**。
不用登面板，不用粘贴任何东西，**跑的永远是仓库里那一版**。

最常改的是 `xhsearch/config.py`：列名、爆文阈值（20/50/100）、
分层刷新间隔、快照里显示几条评论。改完 `git push` 就生效。

改判定逻辑记得跑一遍 `python3 -m unittest discover -s tests -t .`——
792 个测试全离线，一秒跑完，能挡掉绝大部分改坏的情况。

## 附：出问题时按这个顺序查

| 现象 | 先查这里 |
|---|---|
| 表一直不更新 | Railway → Deployments 日志。有没有在跑？Cron 配了吗？ |
| 日志说读到 0 行 | **§3.2 忘了把应用加进表**，九成是这个 |
| `1254045 FieldNameNotFound` | 列名和 `config.py` 对不上，差空格也算 |
| `1254063 MultiSelectFieldConvFail` | 列名对了但**类型**建错了（多半是「流量状态」建成了单选）。跑 `doctor --table 表名` 看是哪一列 |
| 报错里有 `auth` | Key 填错或过期。TikHub 和 SocialDataX 分开看是哪个 |
| 报错里有 `transport` | 网络。TikHub 确认 `TIKHUB_BASE` 设成了 `.io` |
| 报错里有 `quota` | 余额见底。有备胎的话它会自动顶上，但要去充值 |
| 标签被机器覆盖了 | 不该发生——机器只碰它自己那几个值。真遇到请把那一行的截图留着 |
| 一堆行巡查状态突然变「已失效」 | 看有没有打 `🛑 已熔断`。打了就是上游故障，不用管 |

日志里每条错误都带 `request_id`，找供应商排查时把它发过去就行。
