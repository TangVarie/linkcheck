## 一、最关键的那个字段：找到了

TikHub 的 OpenAPI 把评论接口的响应声明成一个**无字段约束的通用对象**，
所以光读文档永远读不出它有没有置顶标记。实测打开发现：它是**上游原始响应的透传**，
置顶信息在里面，只是名字完全不同。

```json
"show_tags_v2": [
  {"style_id": "red", "type": "user_top",  "pos": "cmt_bottom", "text": "Pinned"},
  {"text": "Author", "pos": "post_name", "type": "is_author", "style_id": "red"}
]
```

| 我们要的 | SocialDataX | TikHub（实测） |
|---|---|---|
| 置顶标记 | `is_pinned: true` | `show_tags_v2[].type == "user_top"` |
| 作者本人评论 | `is_author_comment` | `show_tags_v2[].type == "is_author"` |
| 评论总数 | `comment_count` | `comment_count`（含楼中楼）+ `comment_count_l1`（只算一级） |
| IP 属地 | 中文 | **英文**（"Shanghai"），已在归一化层翻回中文 |
| 排序 | `sort_type=default` | `sort_strategy=default`，响应还回显 `current_sort_strategy` 可校验 |

⚠️ **认 `type` 不要认 `text`**：`text` 实测返回的是英文 "Pinned" / "Author"，
账号或地区一变就可能变成中文，认它迟早出事。

这些差异全部挡在 [`xhsearch/providers.py`](../xhsearch/providers.py) 一层里，
`analyze.py` 一行都没改。

## 二、钱：省一半，但省的地方不在小红书

TikHub 有一个**公开、免鉴权**的按端点计价接口（实测可直接 GET，1401 个端点）：

```
https://api.tikhub.dev/api/v1/tikhub/user/get_all_endpoints_info
```

| 端点 | 单价 | 走量折扣 | 免费额度可用 |
|---|---:|:---:|:---:|
| `xiaohongshu/app_v2/get_note_comments` | **$0.010** | ❌ | ❌ |
| `xiaohongshu/app_v2/get_image_note_detail` | **$0.010** | ❌ | ❌ |
| `douyin/app/v3/fetch_video_comments` | **$0.001** | ✅ | ✅ |
| `douyin/app/v3/fetch_one_video` | **$0.001** | ✅ | ✅ |

对照 SocialDataX：**¥0.10/次，全平台一个价**（10 积分 × ¥0.01）。

两件事要划重点：

1. 官网上那个「日调用量 1000 起阶梯折扣」，**对小红书接口不生效**（`allow_discount = 0`）。
   我们 65% 的调用量正好全压在小红书上。
2. 小红书接口 **`allow_free_credit = 0`**，每日签到送的免费额度用不到它。

### 按我们真实的分层刷新算（`python3 tools/estimate_cost.py 20 0.7`）

| | 小红书 415 次/天 | 抖音 224 次/天 | 合计/月 |
|---|---:|---:|---:|
| SocialDataX | ¥1,245 | ¥672 | **¥1,918** |
| TikHub | ¥896 | ¥48 | **¥946** |
| 省 | 28% | **93%** | **51%（¥972/月）** |

汇率按 1 USD = 7.2 CNY，7.0～7.5 之间都是省 49%～52%。

**「省一半」这个总数，一多半是抖音贡献的。** 小红书那段只便宜 28%——
这就是为什么 SocialDataX 值得留着当备胎而不是直接销号：它贵得不算离谱，
但在下面这件事上明显更强。

## 三、失效检测：TikHub 更脏，但够用

这是 TikHub 最弱的一环，也是我们花最多力气挡住的一环。

### 3.1 ⚠️ 传错笔记 ID 照样扣费（对方文档 + 实测双重确认）

> 如果传入错误或不存在的笔记ID，接口仍会正常响应，但 `data` 中会返回上游"服务异常"
> 信息，该请求 **同样会正常计费扣费**。 —— TikHub 接口文档原文

实测更糟：不存在的笔记返回的不是什么"服务异常"，而是一个**看起来完全正常的空壳**：

```json
{"code": 0, "success": true, "msg": "",
 "data": {"comments": [], "comment_count": 0,
          "all_sort_strategies": [],     // ← 活笔记这里有 3 个
          "user_id": ""}}                // ← 活笔记这里是作者 id
```

HTTP 200、`success: true`、没有任何错误信息，**而且扣了 $0.01**。
和「一条真实存在但零评论的新笔记」几乎一模一样。

对比 SocialDataX：`1006 content_unavailable`（封控）、`1008 content_deleted`
（厂商自己标了"不要重试"），语义和处置都写在公开规范里。

**我们的处理**：拿 `user_id` 和 `all_sort_strategies` 当线索判**嫌疑**，
但因为这是启发式而不是厂商契约，**绝不 definitive**——必须走满两击定罪。
账也照实记：`_was_billed()` 会把这类「HTTP 成功、业务失败」的调用算进成本，
只记成功的调用会让账面比账单少。

### 3.2 但 detail 接口的死亡信号是干净的（实测）

| 平台 | 活的 | 死的 |
|---|---|---|
| 小红书 `get_image_note_detail` | `data: [{note_list: [{...}]}]` | **`data: []`** |
| 抖音 `fetch_one_video` | `aweme_detail: {...}` | **`aweme_detail: null` + `filter_list: [{aweme_id, reason: 8}]`** |

这两个是确定性的，代码里一次定罪，不用等第二轮。

⚠️ 但有一条护栏：**评论接口刚拿回一堆评论、detail 却说笔记不存在时，不认 detail**。
那是上游自相矛盾，信它就是拿一次抖动杀掉一条好帖子。见
`runner._looks_alive()` 和 `tests/test_failover.py::test_live_note_is_not_killed_by_a_contradictory_detail`。

### 3.3 顺带白捡的：上游自己的审核标记

| 平台 | 字段 |
|---|---|
| 小红书 detail | `in_censor` |
| 抖音 detail | `status.is_prohibited` / `status.in_reviewing` |

SocialDataX 没有这两个。**目前只写进「诊断信息」提醒人看，不参与打标签**——
只见过 `false`，语义没在真被封的帖子上验过，凭没验过的字段打「风控中」，
一旦误报就是运营全线停投。验过之后再提升，见 [`待验证清单.md`](待验证清单.md)。

## 四、三个实测踩出来的坑（都已在代码里处理）

### 4.1 不带浏览器 UA 直接 403

裸 urllib 的默认 UA 会被 Cloudflare 判成机器人：

```
HTTP 403  {"error_code": 1010, "error_name": "browser_signature_banned"}
```

连业务层都到不了。SocialDataX 裸 urllib 就能通。

处理：`providers.py` 里写死了浏览器 UA，并且**把 Cloudflare 的 403 归类成
TRANSPORT 而不是 AUTH**——归成 AUTH 会把这条通道整轮标死，可它换个网络就好了。

### 4.2 报错信息会把你的 API Key 原样回显

实测（用假 Key 打的）：

```json
{"detail": {"code": 401, "message_zh": "无效的API令牌，您提交的API令牌为 <你的key>。..."}}
```

我们的 runner 会把错误文案写进飞书的「诊断信息」列。照抄就等于**把 Key 写进表里给全公司看**。

处理：`_redact()` 在落库前抹掉，`tests/test_failover.py::TestSecrets` 钉死这条。

### 4.3 主域名在大陆被墙

对方文档原文：`api.tikhub.io` 被防火墙拦截，大陆用户须用 **`api.tikhub.dev`**
（实测该域名可用，同一套接口、同一套鉴权）。

处理：`TIKHUB_BASE` 写死成 `.dev`，测试里钉死免得被人改回去。

## 五、双通道怎么工作

```
                    ┌─ 主通道 TikHub ──── 成功 ──▶ 归一化 ──▶ 判定
调用 ──▶ 选通道 ──┤
                    └─ 网络故障 / Key 失效 / 余额耗尽 ──▶ 降到 SocialDataX
```

配置在 [`xhsearch/config.py`](../xhsearch/config.py) 的 `Channels`：

```python
order = {"xhs": ["tikhub", "socialdatax"], "douyin": ["tikhub", "socialdatax"]}
```

只想用一家就写成单元素，或者用环境变量 `CHANNEL_ORDER=xhs=socialdatax; douyin=tikhub`。
**没配 Key 的那家会自动从顺序里滤掉**，所以只填一个 Key 也能直接跑。

三条规则，每条都有测试钉着：

1. **只有通道故障才降级**（TRANSPORT / AUTH / QUOTA）。
   **「笔记没了」绝不降级**——那是行级结论，换一家只会再花一次钱得到同一个答案。
2. **Key 失效 / 余额耗尽 = 整轮拉黑这家**，不是每行都去撞一次 401。
   600 行各撞一次既慢又会把限流打出来。
3. **所有通道都倒下才算致命**。这正是双通道最值钱的地方：
   以前半夜 Key 失效 = 一整晚的监控全丢，现在只是换一家继续跑。

### 5.1 抖音短链先免费展开，否则抖音根本走不上 TikHub

TikHub 的抖音端点**只收数字 aweme_id，不收链接**，而运营从 App 里复制出来的
几乎全是 `v.douyin.com/xxx` 短链。2026-09 的一次事故把这个盲点暴露了出来：
SocialDataX 积分为 0（错误码 1004），日志报「douyin 平台本轮无可用通道」——
TikHub 明明配着、余额充足，抖音行却一条都没走它。原因就是短链行被 `can_handle`
判成 TikHub 不能接，实际上**抖音一直是 SocialDataX 单通道**，上面那张
「抖音省 93%」的账一分都没兑现。

现在开跑时多了一步（[`xhsearch/shortlink.py`](../xhsearch/shortlink.py)）：

```
抖音短链 ──▶ GET 一次、不跟随重定向 ──▶ 302 Location 里抠 /share/video/<id> ──▶ 换成 aweme_id ──▶ 照常挑通道
```

* **不花钱**：短链对任何 GET 都回 302，我们只要那个响应头，落地页正文不下载。
  但它是一个真实请求，如实计入 `MAX_CALLS_PER_RUN`。
* **只在会改变路由时才做**：有一家可用通道吃 ID 不吃链接（TikHub 配了且本轮
  没被判死）。只配 SocialDataX 的部署它本来就吃短链，不多发这一跳。
* **展不开就退回原路**：短链过期、落地页改版、网络抖动都不报错——按原链接
  交给 SocialDataX；只配 TikHub 时按「跳过」处理，诊断信息里写清展开为什么失败。
  日志末尾的「🔗 抖音短链展开：成功 N，失败 M」一旦失败数抬头，先怀疑落地页
  形态变了，去看 `links._DOUYIN_ID_PATTERNS`。
* **只对抖音自家域名发请求**：每一跳都验 hostname，跳出 `douyin.com` /
  `iesdouyin.com` 就停。链接是运营手工录入的，谁都能往表里贴。
* **一轮之内同一条短链只展一次**。

⚠️ 成功路径按对方落地页的公开形态（`iesdouyin.com/share/video/<id>/`）写，
还没拿一条**真实有效**的短链验过；沙箱里拿两条编造的短链跑过，都跳去了
`www.douyin.com` 首页，按「没抠出 ID」干净失败，没有异常。见待验证清单第 19 项。

## 六、还没验的

见 [`待验证清单.md`](待验证清单.md)。和双通道相关的三条：

1. **TikHub 余额耗尽时到底返回什么** —— 现在靠 HTTP 402/403 + 「余额/充值/insufficient」
   文案兜。对方没有公开的业务错误码表（SocialDataX 有）。
2. **`in_censor` / `is_prohibited` 在真被封的帖子上是不是 true** —— 验了才敢拿它打标签。
3. **抖音的置顶** —— 评论里有 `label_type` / `label_text`，但语义没验过，
   现在一律不判置顶（和之前对你的承诺一致）。
4. **抖音短链展开在真实短链上是否跳到 `/share/video/<id>`** —— 见 5.1 的警告。
   跑一次 `python3 tools/probe_channel.py <一条真实的 v.douyin.com 短链> --only tikhub`
   就能验，探针会打印「🔗 短链已展开」或失败原因。

## 七、第三家：EveryInfra 万有引擎（2026-10-13 评估，结论：不接入）

起因：手上有三家候选（TikHub / SocialDataX / EveryInfra）要选出 linkcheck 的数据源。
逐家看完写进同一份文档，免得下次再查一遍。**本文一~六节结论不变，双通道不动。**

### 7.1 它是什么

统一数据 API 一个端点通吃全部数据能力：`POST /api/v1/social`，请求体三要素
`platform` / `action` / `params`，换平台只改 platform 一个字段。90 个平台、
410 项能力，不止社交内容，还覆盖点评口碑（谷歌地图、Trustpilot、App Store
评论）、电商（Amazon、Temu）和全网搜索。另有验证码识别、全网搜索、发信、
代理、接码等专项 API，以及充值用户免费的 OpenAI 兼容 AI 接口（默认
gemini-3.6-flash，用来清洗/分类/摘要采集回来的数据）。

能力目录 `GET /api/v1/social/catalog` **免鉴权、免费**，带每个能力的必填参数、
单次条数上限和单价。本节所有 EveryInfra 的数字都出自这份目录的原文
（2026-10-13 拉取，脚本按 `platform ∈ {xiaohongshu, douyin}` 过滤）。

### 7.2 小红书/抖音能力清单与单价（目录原文）

**小红书：全部能力同价，400 credits = ¥0.0373/次** —— search / profile /
user_posts / note（详情）/ comments / comments_batch（多链接批量，按成功目标数
计费）/ sub_comments / search_users / hashtag / trending。

**抖音：全部能力同价，40 credits = ¥0.0037/次** —— search / profile /
user_posts / video / comments / trending / transcript（视频文稿）/ creator_search /
creator_audience（粉丝画像）/ creator_trend / creator_benchmark /
**xingtu_creator_search（星图达人搜索）/ xingtu_creator_analytics /
xingtu_rate_card（达人报价）/ xingtu_creator_rankings（达人榜单）** /
product_search / product_detail / live_product_search。

两个平台 comments 的响应字段（目录 `response_fields` 原文，共 18 / 12 个）：

| 小红书 comments（18 字段） | 抖音 comments（12 字段） |
|---|---|
| id, text, like_count, posted_at, ip_location, author_name, author_id, sub_comment_count, note_id, note_url, next_page_token, images, **is_author**, author_avatar_url, author_red_id, author_is_ai_agent, mentioned_users, platform | id, text, like_count, reply_count, author_name, author_id, ip_location, **liked_by_author**, is_reply, reply_to_id, posted_at, platform |

对着本项目横过来看，缺的三样全是硬伤：

- **没有 `is_pinned`**（小红书、抖音都没有）——置顶评论内容这一列直接做不了；
- **两个平台的 comments 都没有 `comment_count`**——评论数在 note/video 详情里，
  是另一个 ¥0.0373 / ¥0.0037 的调用；
- **抖音 comments 没有排序参数**（小红书的 comments 有可选 `sort`，抖音没有，
  口径与小红书不等价）。

作者本人评论有替代字段（小红书 `is_author` / 抖音 `liked_by_author`），这一项不亏。

### 7.3 为什么进不了 linkcheck

三条，每条对着本项目的一处硬约束：

1. **置顶监控直接做不了。** 置顶评论内容是本项目的核心产出列：TikHub 有
   `show_tags_v2`（第一节，已实测），SocialDataX 有 `is_pinned`（值是错的，
   已按不可信处理），EveryInfra 连字段都没有。接进来只能当「评论数 + 评论内容」
   的第三备用通道——而这两件事双通道已经覆盖，第三条通道的边际价值接近零。
2. **失效判定比 TikHub 还弱。** 两击定罪和全局熔断都要求区分「暂时不可访问 /
   已删除 / 被风控」。SocialDataX 有 1003/1006/1007/1008 的权威契约，
   TikHub 靠空壳 + detail 死讯的启发式（第三节），EveryInfra 只有 HTTP 级错误码
   （400 unknown_capability / 402 quota_exhausted / 429 / 503），和 TikHub
   同一类弱，且没有 detail 那种干净的死讯。接它不增加任何判定能力。
3. **算下来并不更便宜。** 按第二节的真实负载（小红书 415 次/天 + 抖音 224 次/天）：

| 通道 | 小红书/月 | 抖音/月 | 合计/月 |
|---|---:|---:|---:|
| TikHub（现状） | ¥896 | ¥48 | **¥946** |
| EveryInfra | ¥929 | ¥50 | **≈¥979** |
| SocialDataX | ¥1,245 | ¥672 | ¥1,918 |

小红书单价看着比 TikHub 便宜 48%（¥0.0373 vs ¥0.072），但评论数得再调一次 note
详情，合计 ¥0.0746/条/天——比 TikHub 一次 ¥0.072 更贵，还少置顶。抖音确实最便宜
（¥0.0037 vs ¥0.0072），但 TikHub 抖音端点 `allow_discount=1`，量上去后差价抹平。

### 7.4 它强在哪、该用在哪

EveryInfra 的问题不是不好，是「宽而不深」：90 个平台的广度 + 归一化字段，适合一次性的、
多平台的取数；linkcheck 要的是单平台、逐条、长期、可判定的深监控。它真正值钱的是
**抖音商业化数据，全部 ¥0.0037/次**：

- 星图达人搜索（`xingtu_creator_search`：含 `quote_1_20s_cny` / `quote_20_60s_cny` /
  `quote_60s_plus_cny` 分档报价、`gmv_30d_range`、`engagement_rate_30d`、

规范说的不算数**，先拿真 Key 跑探针（字段、空响应、错误码）再写进流程。

### 7.5 其他值得记的
