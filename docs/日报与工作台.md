# 项目日报与运营工作台

监控页增加项目工作台：顶部直接展示时段内已检查、当前负面帖子及负面处置三态；检查数字下方显示具体起止时间，另列纳入监测总量和新老帖分批巡检说明，避免将时段检查量误读为发帖总量。下方另列全部异常待办。日报按需展开，正文分行显示，统计说明和人工补充默认折叠。按项目查看、按状态筛选和原来的项目待办标签联动；诊断全文收进详情，保留原来的批量排队刷新、归档及撤销操作。

## 数据链路与此次调整

业务数据库是飞书多维表格。`cli.py` 读取注册表和业务表，`runner.py` 按分层策略扫描；`providers.py` 归一化供应商数据，`analyze.py` 判定，结果回写业务表。面板通过 `panel.collect()`、`summary.py` 读取最新状态。

原业务表仅保存最新检查时刻、负面状态和截断评论快照；原“已解决”存于面板设置的 `todo.resolved`，用于收起待办。它们都无法恢复过去某一天的完整扫描或处置历史。

新增 `daily_report.py` 将成功扫描及运营状态事件持久保存在注册表 base 的“巡检留痕”表。评论保留上游 ID 和创建时间；日报按发现时刻归属，独立于业务表随后刷新的最新状态。原巡检判定和付费请求计划保持原有路径。

工作台同时读取现有业务表，启用留痕前已有的成功检查和负面状态也可立即查看。本期已检查按当前表最近一次成功检查落入所选周期的帖子统计，包含没有异常的正常帖子；刷新失败不算成功检查。当前负面及三态按当前快照统计，不能把“需重新整理”等全部待办当成负面。负面评论数只数规范负面快照中的可见记录，截断或缺少评论 ID 时标为估计／至少；缺列或缺快照显示未知，不用整帖总评论数替代。

当前周期留痕未齐时，复制内容使用现有表快照草稿，并注明来源。已结束的历史周期只用可追溯记录，不用现在的状态冒充历史；没有记录时显示“—”并禁用复制，不生成一段零工作量汇报。

## 操作方式

- 每条帖子支持“待处理／正在处理／已处理”。原“已解决”按钮兼容保留，表示已处理。
- 正在处理的行继续显示。正常重刷保留这个状态；出现新的异常原因时重新提示待处理。
- 已处理沿用原复开规则：后续检查仍检出负面等可复判问题，会重新成为待办；风控等粘性问题继续遵循原来的收起规则。
- 顶部负面处置按当前负面帖子去重计数；次要一行“全部异常待办”按完整待办行计数，包含归档和临时检查记录，不受列表截断或搜索结果影响。一个帖子在表里登记多行时，全部异常待办可以是多行。
- 浏览器可见时每 15 秒同步待办，每 60 秒同步日报；后台业务表默认每 60 秒读取。状态操作成功立即同步。自动更新不整页刷新，保留选择、输入和滚动位置；隐藏标签页暂停轮询。

## 日报统计口径

时间按北京时间：所选截止日的前一天 16:00 至当天 16:00，左闭右开。16 点前为预览；截止后按截止时的历史记录还原。下一周期开始后可以查看下一截止日，支持最近 90 天查询。

| 指标 | 含义 |
| --- | --- |
| 成功扫描帖子 | 本窗口成功取得评论页的帖子，按项目内平台及作品 ID 去重；失败、冷却、跳过不算成功扫描 |
| 扫描观测次数 | 成功扫描观测记录数；同帖重复登记或复查可以产生多次观测，并非付费 API 调用次数 |
| 预警帖子／评论 | 本窗口扫描检出的负面或竞品词预警；同帖评论优先按上游评论 ID 去重 |
| 三态帖子／评论数 | 本窗口检出预警集合截至截止时的整帖处理状态；评论数随其所属帖子统计 |
| 本期运营操作 | 本窗口人工标记状态的去重记录，包含本期没有重新扫描的存量问题；同一记录可以先开始处理、后完成，因此各操作数不相加求总量 |
| 集中时段 | 评论在本窗口首次检出的小时；并非评论实际发表的高峰 |
| 主要命中词 | 来自原有负面判定的命中词计数，是内容线索，不能等同语义分类 |

只扫描第一页，报告是预警工作记录。它不等于全部评论普查，也不能把“本期检出”写成“本期新增”。缺上游评论 ID 时按同帖正文归一化去重，结果标为估计，相同文案可能合并。

“主要内容特征”和“疑似竞品”**默认由 AI 自动生成草稿**：选中单个项目、日报载入后，面板调用 DeepSeek 官方 `deepseek-flash` 归纳本期预警帖子标题（只取当前还没处理完、原因是「有负面」的帖子；风控、失效、卡住不算预警帖子）与第一页预警评论，填入两个输入框；运营只需改错、补充，不必从空白开始写，人工内容永远不会被 AI 覆盖。草稿与修订都按项目和日期保存在当前浏览器，复制时并入汇报。

外发内容只包含运营写的帖子标题、去重后的预警评论正文（已替换链接、邮箱、手机号、@账号）与命中词；不发送昵称、IP 属地、作者信息、record_id、普通评论快照或浏览器里的修订。同一份证据 15 分钟内只调用一次，多人看同一项目共用结果（「同一份」按真正送给模型的内容认，当期日报的截止时刻每分钟往前走不算新证据）；「重新生成」有 30 秒服务端冷却，同时到的两次只外呼一次；未配 `DEEPSEEK_API_KEY`、超时或返回不可解析时整块降级为人工填写，并给出可重试的提示。

竞品名必须逐字出现在预警评论或命中词里，否则面板直接丢弃——模型不能靠常识补品牌。只出现在帖子标题里的不算：标题是运营给自家帖子写的，自家品牌和对比测评里的名字都在里面。没有可靠竞品分类字段这一条没变：这里给的是**线索**，不是结论，也不能把所有负面命中词当竞品。

跨项目查看时，各项目分别统计；同一作品归属多个项目，可以分别计入，不能理解成跨项目全局作品去重。

## 留痕与故障恢复

需 cron 和面板都使用相同的 `FEISHU_REGISTRY` 及飞书应用凭据。无需引入 SQL、依赖包或容器持久盘。

1. 部署包含本次修改的 cron 与面板版本。
2. 首次有实际待刷行时，由 cron 自动在注册表 base 建立“巡检留痕”表，保存项目启用时刻。面板只找已有表，避免两个服务同时建出同名表。
3. 第一个周期可能只有部分时段，界面和复制文案明确标示覆盖不完整；启用前的历史无法补算。
4. 扫描留痕按项目、类型装箱并分片追加，携带稳定幂等键和内容校验。重复返回去重，缺片整箱不参与统计并显示缺口。扫描前后批次记录用于识别中断；没有待刷行的空轮不写批次。一轮在截止前开跑、截止后收尾的算闭合；开跑不到 2 小时还没收尾的算进行中，不报未闭合。
   处理状态要读到截止时的全部历史：面板首次整段读，之后只补读最近两天、每 6 小时整段重读一次纠偏；面板自己补写的状态直接记进内存。
5. 状态变更与待补写事件在同一次面板设置更新中保存。留痕暂不可写时，页面状态仍保留并提示待同步；后续日报请求自动补写，重启后也能继续。待补写事件有容量上限，积压过多时丢弃**最早的**待补写记录（运营照样能点，不会被拦住），并提示丢了多少；恢复后丢掉的那段作为留痕缺口一起写进去，相关日报标覆盖不完整。
6. 留痕写入失败不丢弃原有巡检结果，CLI 明确警告并返回非零；日报显示不完整，仍需结合运行日志核对。留痕表追加保存，无自动删除；长期运行需按飞书表容量安排归档。

日报 API 仅返回汇总、命中词及可复制文字，不返回原始评论正文。新接口沿用面板会话认证；状态写入沿用 CSRF 校验，并核对完整服务端待办及检查版本，拒绝伪造 ID 和旧扫描结果。
