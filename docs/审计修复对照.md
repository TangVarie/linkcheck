## 6. 行为变化（升级时要注意的）

1. **元数据读不到时不再继续跑**。以前是「不过滤，宁可试着写」，现在直接拒跑并提示去跑 `doctor`。表现是：飞书权限/网络出问题时，任务会明确失败而不是先花钱再赌写回。
2. **`MAX_CONCURRENCY` 只接受 1–3**，越界拒绝启动。之前设了 4 以上的部署需要改回来。
3. **小批次也会熔断了**：一批里每一行都栽在同一个非权威错误码上（≥3 行）就整批作废判定。真被删掉的内容拿到的是权威码，不受影响。
4. **`CHANNEL_ORDER` 里同一家排两遍会拒绝启动**（以前静默接受）。
5. **`.env` 里有看不懂的行会拒绝启动**（不只是解析变严格）。未配对的引号、非法变量名会被列出来并退出——悄悄跳过一行畸形配置，产生的是一个「看起来配好了、实际值不对」的部署。行内注释需要用空格隔开 `#`。
6. **默认锁文件位置变了**：从 `/tmp/linkcheck.run.lock` 改成 `$TMPDIR/linkcheck-<uid>/run.lock`（每个用户一个 0700 私有目录）。显式配了 `RUN_LOCK_PATH` 的不受影响。
7. **供应商返回的成功响应形状不对时会降级到备胎**（原来只把行判失败，备胎一次都不试）。

### 三个闸门的强度，说清楚

被追问两轮之后，这件事值得写死在文档里（也写进了 `config.Budget` 的 docstring）：

* `MAX_YUAN_PER_RUN` —— **硬上限**。悲观预留 + 事后 settle，任何一行都顶不穿它。
* `MAX_CALLS_PER_RUN` —— 记的是**实际发出的 HTTP 请求数**（含重试和降级）。
  预留覆盖降级，但传输层重试（最多 3 次，只在网络故障/5xx 上发生）无法提前预留，
  所以单行最多超出它自己的重试次数，超出部分在下一行的闸门上体现。**要卡死钱就用金额闸门。**
* `MAX_RECORDS_PER_RUN` —— 精确的行数闸。
